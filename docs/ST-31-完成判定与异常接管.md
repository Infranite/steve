# ST-31 完成判定、收尾失效与 Steve 异常接管

以 ST-25 为案例，核对“Agent 停下来了”“冻结之后结果又变了”两类提示的成因，并修改判定逻辑。

## ST-25 事件链（2026-11-04）

| 时间 | 事件 | 原因 |
| --- | --- | --- |
| 20:14 | 交付，你验收通过 | 项目配置了本机发布，收尾等待“发布上线”这一必需操作 |
| 20:14 | 你拒绝本机发布，要求走 GitHub PR 流程 | 收尾仍在等待本机发布 |
| 20:16–20:18 | Agent 把分支 rebase 到新的 main，并提交 `docs/releases/0.2.21.md` | 指纹由 `HEAD` 和整棵树组成，两项都变化 |
| 20:18:56 | **收尾作废：冻结之后结果又变了** | rebase 本身也会触发作废；Agent 没有收到作废通知 |
| 20:21 | PR 已合并，v0.2.21 tag 已推送；Agent 在后台等待 Release 构建并结束回合 | Agent 认为 20:14 的交付仍然有效，剩余工作只有“等构建” |
| 20:22:06 | **Agent 停下来了，没有交付也没有提问** | 停止后直接生成异常卡；你 90 秒前刚操作过，YOLO 按在场规则让给你处理 |
| 20:23:27 | 重新交付并自动验收 | — |
| 20:23:42 | Agent 执行 `git reset --hard origin/main`，切到 GitHub 重写后的同内容提交 | 内容完全相同，只有 `HEAD` 不同 |
| 20:23:55 | **再次收尾作废** | 属于误判：指纹包含 `HEAD` |

结论：工作没有中断。这次异常包括两个误判和一个缺口：一是 `HEAD` 变化或 rebase 被当成结果变化；二是系统不知道你约定的“PR 合并且 tag 推送即完成”，只认本机发布；三是交付作废后没有告诉 Agent，Agent 停下后系统也没有先核对就直接通知你。

## 改动

### 冻结结果：按内容和自身改动判断

- 指纹改为 `HEAD:tree:base:patch`。`base` 是分支与本地或远端默认分支的最近合并基点，`patch` 是自身改动的 `git patch-id --stable`。
- 以下情况视为结果未变：内容相同，例如 reset 到合并后的同内容提交或修改提交说明；改动相同但基线不同，例如 rebase 到新的 main。
- 新增或修改文件仍会作废。作废原因会列出变化，例如“冻结之后结果又变了：分支换到了新的基线，改了 docs/releases/0.2.21.md”，并且只列出本事项自身涉及的文件。
- 旧格式指纹 `HEAD:tree` 仍按内容比较，升级后不会因格式变化触发作废。

### 作废后告诉 Agent

- Agent 正在等待你的批准或回答时，作废原因会附在下一条消息前。
- Agent 空闲时，Steve 立即让它继续，并计入续跑次数。
- 提示语要求 Agent 重新交付，并且不要重复推送、合并、打 tag 或发布。

### 项目完成标准（`release.done_when`）

在项目的 `release` 配置中新增可选字段。也可以在“项目 → 设置 → 完成标准”中选择：

| 取值 | 含义 |
| --- | --- |
| 不设置 | 和以前一样：验收后需要在本机发布上线，事项才结束 |
| `merge` | 自身提交已合并到远端默认分支，即 PR 已合并 |
| `tag` | PR 已合并，并且已推送包含这些提交的 tag |

- 核对方式：Steve 先 `git fetch --tags origin`，再用 `git cherry` 和 patch-id 识别 rebase merge 或 squash merge 后的副本，然后通过 `git ls-remote --tags` 确认 tag 已推送并包含该副本。网络命令最长 60 秒，并在锁外执行。
- 验收后，“发布上线”这一必需操作改为核对上述完成标准。未满足时，Agent 只会收到一次提示，说明还差什么；Steve 每 2 分钟复核一次。Agent 每次结束回合后都会立即复核。
- Release 构建作为独立操作 `release.build` 跟踪，不影响完成判定，也不计入“进行中”。Steve 每分钟通过 `gh run list --branch <tag>` 查看一次状态：成功只写入时间线；只有失败时通知你，而且同一次失败只通知一次；超过 3 小时仍未结束或查询不到时，停止跟踪。ST-57 起，事项目标要求构建通过时，这次构建成为必需操作，成功后事项才结束，见 [ST-57](ST-57-完成条件与证据.md)。
- 会话协议会告诉 Agent 这个项目的完成标准，并要求它不要为了等待构建而保留回合。

### Agent 停下后，Steve 先核对

Agent 结束回合时没有交付、提问或待批准事项，或者会话空闲超过 2 分钟时，按以下顺序处理：

1. 最后一句话是问题：直接交给你，和以前一样。YOLO 开启时可以代答。
2. 项目设置了完成标准，并且本周期交付过：Steve 在锁外核对远端。达到标准时，Steve 记录证据并自动完成事项，不需要你处理。
3. 其他情况：Steve 带着核对结果、计划中未完成的步骤和“不要重复对外动作”的提醒让 Agent 继续。默认连续最多 2 次；你在事项上做任何操作后，次数重新计算。
4. 续跑次数用完，或者已经没有会话可以续跑：创建一张异常卡，标明“Steve 已让它继续 N 次”。YOLO 看到这个标记后不会再次自动续跑。

由你中断的回合不会被 Steve 自动续跑。

### 幂等、上限与去重

- 同一次停止被重复上报时，如果续跑回合已经开始或消息已在队列中，就不会再次续跑，也不会创建异常卡。
- 同一事项同一时间只运行一次远端核对；超过 5 分钟没有结果，视为该次核对已丢失。
- 远端核对结果返回前如果出现新回合、消息或卡片，这次结果会被忽略。
- 自动完成复用原有的收尾提交，每个周期只能提交一次。必需操作的状态写入后不会被覆盖；构建失败只在状态首次变为失败时通知。
- 只保留一张异常卡：问题相同的卡片不会重复创建；有新情况时，旧的停止或异常卡会失效，等待你核对外部结果的卡片除外。

## 配置

- `STEVE_TAKEOVER_CONTINUES`：Steve 连续续跑的次数，默认 2；设为 0 表示停止后直接通知你。
- `STEVE_GH`：用于跟踪构建的 GitHub CLI。默认依次查找 `/opt/homebrew/bin/gh`、`/usr/local/bin/gh`、`/usr/bin/gh`，最后使用 `PATH` 中的 `gh`。
- Steve 项目要按 PR 合并和 tag 推送判定完成，需要在项目设置中把“完成标准”改为“PR 合并并推送 tag”。本次没有修改线上数据。

## 未覆盖

- 会话出错，例如“会话出错：…”，仍按原有方式处理：直接创建异常卡，YOLO 开启时按原退避规则重试。Steve 只会对 Agent 自行停下的情况做核对。
- TS Hub（`hub/`）未同步，默认使用 Rust Hub。
- `gh` 不可用时，构建状态只记录到时间线，不会通知你。
