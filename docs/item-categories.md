# 事项分类标签（ST-34）

每件事项必须且只能有一个**分类标签**，另外可以有任意多个**领域标签**（项目、领域、客户、主题）。

| 分类 | 适用范围 |
|---|---|
| `bug` | 修复错误、故障或不符合预期的行为 |
| `feat` | 新增能力、交互或功能改进 |
| `doc` | 文档、方案、说明的编写与更新 |
| `refactor` | 不改变外部行为的代码重构 |
| `ops` | 部署、升级、运维与环境配置 |
| `chore` | 依赖维护、工具配置等杂项 |

混合事项按主要验收目标选分类；目标彼此独立时应拆成多件事项。

## 存储

分类就是 `tags` 表里类别为 `类型` 的六行，每个工作空间各一套，没有新增表或迁移，回滚到旧版本也能读。

- `steve_store::kinds::ensure`：建工作空间、`ensure_workspace`、写事项标签时补齐这六个分类，可以重复执行。如果已有同名标签，就把它改成分类，保留原来的 id 和使用记录；`类型` 下的其他旧标签移到 `主题`。
- `类型` 只放这六个分类：不能新建别的分类，不能删除、合并分类，分类的名称和类别不能改，描述可以改。
- 联系人、团队等对象的标签（`entity_tags`）不接受分类。

## 统一校验

事项标签的每次写入都经过 `kinds::checked`。任务事项的标签里分类数量必须正好是一个，否则返回 `StoreError::Conflict`，HTTP 状态码为 409，并且什么都不写入。

| 写入入口 | 路径 |
|---|---|
| 新建事项（对话分流、`POST /api/items`、流程节点、邮件、渠道规则、派生） | 都走 `Core::create_item` → `kinds::settle`；事项和标签在同一次写入中完成 |
| 修改事项标签（`PATCH /api/items/:id {tags}`） | `Tags::set_item`；标签最先写入，被拒时标题等字段也不会改 |
| 标签管理（`/api/tags*`） | `Tags::create/patch/remove/merge` 内置保护 |

`items().create` 在不带标签时仍然允许创建，只给测试夹具这类底层调用用。所有生产入口都经过 `Core::create_item`，它总会带上一个分类。

## 自动分类

- 分流提示词单独列出六个分类，要求模型在 `tags` 里只选一个并排在最前；`parse_route` 最多保留一个分类。
- 调用方没有指定分类时，`kinds::guess` 按标题和目标里的关键词判断。标题里的关键词权重加倍；什么都匹配不到时归为 `feat`，并标记为“拿不准”，不会默认归为 `chore`。
- 用户改分类就是一次 `PATCH`：新分类替换旧分类。时间线会记录“分类改为 X（原来是 Y）”。

## 历史补齐

`Core::backfill_kinds(ws, dry)`：

1. 找出分类数量不是 1 的任务事项，包括已完成和已归档的。
2. 用 `route` 用途的模型批量判断，每批 20 件；模型调用失败或漏判时，改用 `guess` 判断。原来有多个分类的事项，只能在这几个分类里选一个。
3. 模型给出的置信度低于 0.7，或者靠规则兜底但线索不足（包括从多个分类里挑一个）的事项，记为“拿不准”，写入设置项 `kinds_review`。这些事项会列在“设置 · 标签 · 待确认的分类”中。用户改了分类或点“没问题”后，事项就从列表里移除。
4. 已经恰好有一个分类的事项不会被改动。所以重复执行时，第二次没有任何写入。

Hub 每次启动时都会对所有工作空间执行一次补齐。也可以手动执行：`POST /api/tags/kinds/backfill {dry?}`；`GET/POST /api/tags/kinds/review` 用来读取或确认待确认列表。

## 界面

- 分类用描边小标签显示，前面有一个低饱和度的色点，固定排在最前，不能单独移除；领域标签仍然是灰色小标签。手机上的事项列表只显示分类。
- 事项详情页有“分类”下拉框，用来一步切换分类；“标签”区域只管理领域标签。
- 事项列表可以同时按“全部分类”和“全部标签”筛选，两个条件需要同时满足。
