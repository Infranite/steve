## 2. 完成条件按事项目标设定

Steve 读事项的标题和每一版目标，找出要证明的三类结果（`hub-rs/crates/steve-core/src/proof.rs`）：

| 目标里出现 | 要的证据 | 怎么取得 | 没取得时 |
|---|---|---|---|
| 构建通过、构建成功、确认构建、Release 构建、流水线、CI 通过 | **构建通过** | 项目按 tag 判完成时，tag 触发的 Release 构建变成必需操作，构建成功才关闭；不打 tag 的项目以 Agent 交付里的构建检查为准 | 构建中：事项停在“正在结束：等 Release 构建（vX）成功”。构建失败或 3 小时没结果：告诉 Agent 去修，同时通知你；事项不关闭 |
| 当前实例、本机生效、实例升级、部署到、发布上线、已上线 | **部署生效** | Steve 自己的项目：tag 推送后，核对本机运行的版本是否包含它（有构建提交时按提交祖先关系，本地构建按 `-local-<提交>`，否则按版本号不低于 tag）。每次检查收尾门都会再核对一次，升级重启后自动关闭 | 停在“等本机运行包含 vX 的版本”，时间线写明本机现在的版本，通知你一次 |
| 验证、实际操作、实测、截图、端到端 | **实际操作验证** | `steve_deliver` 至少有一条通过、并标了 `operated: true` 的检查，例如“设置·关于点检查更新，显示 v0.2.46”；构建和测试不算。交付里显示为“✓ 实际操作：…” | 交付被退回，说明缺什么；Agent 停下时远端已合并打 tag，也不再按远端证据自动关闭，而是让它补上实际操作再交付 |

- 其他项目要求“部署生效”时 Steve 看不到目标环境，按“实际操作验证”处理：Agent 在部署的地方实际核对，标 `operated: true`。
- **你自己点「标记完成」就是证据**，以上条件都不再拦。确认某件事不需要构建或部署证据时，用这个办法结束。
- 目标里没有这些要求的事项，完成条件和以前一样（项目约定的合并 / 合并并打 tag）。
- Agent 开始工作时，协议里会多一行，写明这个事项的目标要它证明什么。
- 识别靠关键词，可能多判或漏判。多判时你标记完成即可；漏判时，在目标里写明“确认构建通过”“在本机生效”“实际操作验证”这类字样。
