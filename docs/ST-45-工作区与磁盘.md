# ST-45 任务工作区：测量、选型与回收

## 1. 现状测量（2026-11-05，本机 APFS，Steve 自己的仓库）

| 对象 | 数量 | 占用 |
| --- | --- | --- |
| 源码（一个工作区去掉依赖和构建产物） | 每个工作区 | 约 16 MB，约 1,200 个文件 |
| Git 对象库（所有工作区共用） | 1 份 | 552 MB（两个包，16,855 个对象） |
| `node_modules`（根目录和 `web/`） | 每个工作区 | 350–630 MB，约 3.4 万个文件 |
| Rust `hub-rs/target` | 每个构建过的工作区 | 2.5–17.5 GB，最多约 6 万个文件 |
| `~/.steve/worktrees` 合计 | 22 个工作区 | 约 103 GB，其中构建缓存约 79 GB、依赖约 12 GB |

结论：

- **空间几乎全是可重建的缓存。** 源码只占 0.3%，Git 对象本来就共用，所以换一个 worktree 工具或改成共享对象库，省下的空间都可以忽略。
- **回收一直没生效。** 17 个已结束事项的工作区还在。有两个原因：
  1. 已完成的事项要等分支“已合并”才删工作区，但 PR 用 rebase 合并后提交号会变，`merge-base --is-ancestor` 永远判断为未合并。实测 ST-27、29、30、32、33、35、37、39、42 的提交在 `git cherry` 里都已在 main 上。
  2. `git worktree remove` 会连带删除被忽略的 `target/`。删除十几 GB 要好几秒，这期间 Hub 的状态锁一直被占着。
- **一次构建的写入量（`cargo test --workspace --no-run`）：**

  | 构建方式 | 写入量 | 文件数 | 耗时 |
  | --- | --- | --- | --- |
  | 冷构建，默认 profile | 15.1 GB | 5.6 万个 | 238 秒 |
  | 冷构建，`debug = "line-tables-only"` | 12.2 GB | 5.6 万个 | — |
  | 先用 APFS 克隆一个已构建的 `target` 再构建 | 17.6 GB 新写入 | 只编译 62/606 个 crate | 172 秒 |

  - 第二行的 CPU 时间比第一行少 16%。它和其他 Agent 的构建同时运行，所以墙钟时间不可比，表中没有列出。
  - 第一行的 15.1 GB 里，测试可执行文件约 6.4 GB，增量缓存约 6.2 GB，其余是依赖的 rlib 和 macOS 调试信息 `.o`。
- **读写压力：** 有一个 `npm ci` 在跑时，磁盘持续在 5,000–9,000 IOPS、80–140 MB/s（`iostat`）。高并发下的压力主要来自每个工作区各自做一次冷构建和完整的依赖安装，Git 操作只占很小一部分。

## 2. 方案评估

| 候选 | 能做什么 | 对空间的作用 | 结论 |
| --- | --- | --- | --- |
| Worktrunk（Rust，MIT/Apache-2.0，活跃） | 管理工作区；用 reflink 复制被忽略的文件；删除前判断分支是否已合入（含 rebase、squash、patch-id） | 能把缓存的复制变成写时复制，但不减少后续构建的写入 | 不作为依赖引入。Steve 已经有事项、会话和发布的生命周期，再接一层外部状态会重复。借鉴它的合入判断和后台删除 |
| git-worktree-runner、git-wt、phantom、gwq、ccmanager | 管理工作区，复制或链接文件，运行钩子 | 没有 | 不采用 |
| `clone --shared/--reference`、partial clone、sparse checkout | 共享或减少 Git 对象 | 只影响 552 MB 的对象库 | 不需要：worktree 已经共用对象库 |
| 多个工作区共用一个 `CARGO_TARGET_DIR` | 同一份构建目录 | 能省空间 | 不采用：Cargo 的构建锁会让并发构建排队，各分支的产物还会互相覆盖，破坏隔离 |
| sccache | 缓存编译结果 | 依赖 crate 能命中，工作区自己的 crate 因路径不同不命中，也不缓存增量编译 | 暂不引入，收益只在依赖部分 |
| APFS / reflink 克隆已构建的 `target` | 新工作区开工就有依赖的编译产物 | 实测编译时间少 28%，但新写入不少 | 第二阶段再考虑：省的是时间不是空间，而且要处理克隆和构建之间的竞争 |
| pnpm 或 bun 的全局存储（硬链接或克隆） | 依赖去重 | 每个工作区约省 0.5 GB | 要换项目的包管理器，不由 Steve 决定 |
| 随包分发 Git（dugite-native，GPL-2.0）或 gitoxide | 不依赖用户的 Git | — | dugite-native 有 GPL 分发义务。gitoxide 还不能删除或修复 worktree。本轮只做可替换的入口 |

## 3. 选型

- **Steve 自己管理工作区的生命周期，仍用标准 Git 仓库格式。** 用户随时可以用普通 Git 检查、接手和恢复。
- **Git 入口统一。** 领域层所有 git 调用都经过 `git::command()`，用 `STEVE_GIT` 可以指向 Steve 管理的固定版本。工作区页面显示当前 Git 版本，判断 rebase 和 squash 合入需要 2.38 以上。随包分发 Git 留到许可和多平台构建确定以后。
- **回收的对象是缓存，不是源码。** Rust `target`、`node_modules` 和常见工具缓存在被 Git 忽略、里面没有被跟踪的文件时，可以随时删掉再构建。判断规则：
  - 目录带 `CACHEDIR.TAG`（Cargo 会写），或者名字是已知的缓存目录名；
  - 被 `.gitignore` 忽略；
  - `git ls-files` 在里面找不到文件。
- **本仓库的调试构建只保留行号表**（`[profile.dev] debug = "line-tables-only"`）。panic 回溯仍然有文件和行号，构建体积少约 19%。

## 4. 生命周期与回收规则

| 时机 | 做什么 | 不做什么 |
| --- | --- | --- |
| 事项结束（完成、放弃） | 立即把缓存移入 `worktrees/.trash`（同一个卷上 rename，瞬间完成），锁外删除。工作区干净，并且分支已合入 main（包括 rebase 和 squash 合入）时，删除工作区 | 有会话在运行、工作区里有进程，或者有未提交的改动时，都不动 |
| 事项归档 | 工作区干净就删除，即使分支没合入。分支保留，时间线记下分支和提交号，继续时从分支重建 | 删除分支（只有完全合入的分支才用 `branch -d` 删除） |
| 每 10 分钟巡检 | 依次做下面几件事：<br>- 删掉回收站里剩下的内容<br>- `git worktree prune`<br>- 回收已结束事项的缓存和可删的工作区<br>- 剩余空间低于 `low`（默认 40 GB）时，从最旧的开始，回收闲置超过 24 小时的进行中事项的缓存，直到空间回到 `low` 以上 | 拿不到进程列表时，不碰进行中的事项 |
| 新建工作区之前 | 剩余空间低于 `floor`（默认 10 GB）时拒绝新建，事项以“磁盘空间不足”失败，同时触发一轮回收；处理好以后可以重试 | 已经有工作区的事项照常继续 |
| 仍然低于 `floor` | 每个工作空间收到一条通知；回到 `low` 以上之后，再次低于时才会再提醒 | — |

阈值通过 `STEVE_DISK_FLOOR_GB`、`STEVE_DISK_LOW_GB`、`STEVE_WORKTREE_IDLE_HOURS` 配置。设置 · 数据与隐私 · 工作区与磁盘列出每个工作区的大小、缓存、状态、没有事项对应的目录和待删除的空间，并可以立即回收一轮。这些信息只对实例管理员显示，因为里面有本机路径。

## 5. 恢复方案

- **交付保全：** 删除之前都要确认工作区干净；分支保留（只删已完全合入的）；时间线记下删除时的分支和提交号。已删除的工作区在事项继续时由 `ensure_cwd` 从分支重建，缓存在下一次构建时重新生成。
- **中断恢复：** 缓存先 rename 进回收站，再删除。Hub 在任何一步退出，回收站里剩下的内容都会在下一轮巡检里删掉，时间线照常记录释放的空间。删到一半的工作区目录由 `git worktree prune` 清掉登记，事项继续时重新创建。
- **并发隔离：** 同一时间只跑一轮回收（另一个调用者会得到 `skipped`）。每个事项的检查和移动都在状态锁里重新确认，确认它没有忙碌的会话、仍然闲置，然后才 rename。删除和测量都在锁外进行。
- **人工恢复：** 回收站在删除前就是普通目录，可以直接移回。分支可以用 `git worktree add <路径> steve/<id>` 手工恢复。

## 6. 验证

- `steve-core` 单元测试 `tests::workspace`，共 9 项：
  - 缓存识别：被忽略的嵌套缓存会被识别；被跟踪的 `node_modules`，或带标记但没有被忽略的目录，不会被识别。
  - 已结束事项：rebase 合入的工作区被删除，分支保留，之后能重建。
  - 保留规则：未合入的工作区归档前保留，归档后删除且提交还在；有未提交改动的工作区保留。
  - 运行中保护：忙碌的会话和工作区里运行的进程（`sleep`）让工作区原样保留。
  - 中断恢复：回收站里剩下的内容和删到一半的工作区，下一轮会清理干净。
  - 低空间：只回收闲置事项的缓存。
  - 低于下限：不新建工作区，已有工作区的事项照常开会话。
  - 占用报告和只跑一轮。
- Hub 接口测试 `tests/workspaces_api.rs`：阈值从配置读入，报告列出没有事项对应的目录；立即回收在启动巡检之后执行，不删除这些目录。
- 已知无关失败：`modules` 测试里的 `knowledge_*` 两项在 main（94f0a4a0）上同样失败。`upgrades::tests::github_checks…` 单独运行通过，只在全量并行、机器负载高时失败。
- 实际释放：`reclaiming_frees_the_disk_space`（`--ignored`，需要手动运行）。在一个已结束事项的 `target` 里写 2 GiB，回收一轮后，卷上的可用空间增加 2.0 GB（386 GB 到 388 GB）。
- 前端：
  - `web/test/disk.test.mjs`：格式、排序、阈值文案、回收提示。
  - `web/test/disk.browser.mjs`：1440 px 和 390 px，浅色和深色，没有横向溢出；立即回收后列表刷新；非管理员不显示这一节。
