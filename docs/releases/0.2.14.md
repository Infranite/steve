# Steve v0.2.14

A safety gate for upgrades and rollbacks. An older Steve can no longer be started on a database a newer one has migrated.

- The database records the oldest version that may open it, and Steve checks this before it touches the database. A Steve that is too old refuses to start and says why, instead of opening the database and writing to it.
- Every way of switching to another release checks the same rule first. That covers `release.sh --rollback`, the undo after a YOLO release, a release whose health check fails, and the local deploy script. A rollback the database doesn't allow is refused before anything is stopped. When a new release fails after it has migrated the database, Steve does not switch back to a version that can't read the data: the failed release stays in place, marked degraded, the error names the backup taken before it, and YOLO hands the decision to you instead of retrying.
- Rolling back to the old TS Hub is gone: `release.sh --rollback ts` and `STEVE_HUB_IMPL=ts` no longer exist.
- A release without the signing keychain, or whose database backup fails, now stops instead of continuing.
- The build and deploy scripts for this machine are now in the repository (`ops/local-release.py`). They use Steve's own maintenance drain instead of a one-time check for running work, lift it once the new version answers, and put everything back when a step before the switch fails. `/healthz` now shows whether that drain is on (`drain`).
- A YOLO undo only offers a rollback the database allows. The rollback's result (done or failed) is noted on the item, and the undo counts as done only once the rollback went through.
- Released migration files are locked by hash; changing one fails the tests, and CI checks the lock only grew since the last release.

The database gets one small bookkeeping table (`schema_compat`); the schema stays 26. Hub and Web must come from the same release. No new provider permissions are requested.
