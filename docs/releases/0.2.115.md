# Steve v0.2.115

- When a message to your own account is handed over to you, its card now reads in words instead of the Hub's ids (`draft_reply`, `to_item`, `done`): **Make it an item** (转成事项), **No reply needed** (不用回复, marks the message handled without sending anything), and a field where you write the reply, sent with **Draft reply** (起草回复). The reply becomes a draft that goes out only after you approve it. Choosing one of these options works again: the card used to answer in a form the Hub rejected.
- The card for a reply that didn't go out now offers every choice the Hub gives it, by name: **Send again** (重新发送), **Don't send it** (不发了) and, when it may already be out, **It went out** (已经发出了). Before, it only offered "retry release", and a send blocked by a missing permission had no button at all.

The README and the deployment guide now say which output is reviewed and how changes get merged:

- Only your private chat with Steve and a Bot's replies to workspace members go without a model's review. Anything sent in your name to someone else passes the rule check and a second model's disclosure check and is held when either fails; a mail draft written while YOLO is off still has the rule check only, which is being fixed. YOLO does not send to people outside your organisation unless you allow it. Others' trigger words on your account are still screened first. See "Outbound checks" in the deployment guide.
- Review findings are blocking or not by a fixed category table (correctness, security, data loss, goal not met, failed required check block; style, naming, documentation, optional optimisation go to a carry-over list the delivery must answer), and a code change made without a work graph is merged by you from a card, not automatically. Both are documented as the target and are being implemented.
- The default rules of Steve's own developer Bot now say: plan and implement one scope in the same unit, and leave review to the independent review Bot. An existing Bot keeps the rules it has; change them on its settings page.

- Work graphs: the item that coordinates a graph now ends its turn once the graph runs instead of waiting and re-reading it. Each time a unit delivers or fails, Steve wakes it with a message marked as coming from Steve (not from you) that says which unit, its result and attempt, a short summary (up to 500 characters), where the graph stands and the next step. Coordinators spend fewer long turns and fewer tokens.
- Retrying a unit waits only for that unit and the units after it (its review, the integration); other units of the graph keep running.
- Work units no longer stumble on their first calls: their brief names the parent item as `parent_item`, they find their upstream results in it without asking again, and reading another item says which item the session may read. Several contradictory instructions to agents were corrected, including the description of open plan steps on delivery.

- A read-only channel connection no longer retries and asks about every message. When the channel service forbids sending, for the whole connection or for one chat, the first refused message opens one card that says why and how to allow sending (for example, give the connection's credential the send permission at the channel service). For the next 24 hours Steve writes no automatic replies or acknowledgements there. Messages you, a flow or an agent still send there are kept in the conversation as not sent, without another card. Once the channel service reports that sending is allowed again, or a message there goes through, this ends at once.
- YOLO now resends a message or mail whose send failed at most twice (setting `chan_retry_max` in the YOLO policy). After that, the card stays for you. A send that can never work (a read-only connection, a missing permission) is not resent at all.

Design confirmation is now a switch on the item, **Design confirmation** in the item's properties, off by default. Steve no longer guesses it from words in the goal such as "先出设计" or "设计通过后再实现", so an item whose goal only mentions a design is delivered for acceptance like any other. Only the instance's owner can turn it on or off, on the item page or with `PUT /api/items/<id>/design-gate {"on": true}`. Bots, MCP tools and YOLO have no way to change it. When it is on, a delivery stops at the design card (implement the design, keep the design only, or revise it), and YOLO still never answers that card. Once you choose to implement the design, the implementation is delivered for ordinary acceptance with the switch still on. If the goal changes after that, the next delivery stops at the design card again. The delivery text is always saved as a design file Steve can verify, so an external link or a file that doesn't open in the browser next to it no longer gets the delivery refused.

When Steve refuses a delivery, the reason now shows in the item's activity, and the next time Steve continues the agent it passes the reason on. If a delivery is refused twice in a row for the same reason, the item comes to you instead of the agent being asked to deliver again. `STEVE_TAKEOVER_SAME_REFUSALS` sets the number of refusals (default 2, 0 turns it off).

A trigger word that needs the machine is now handed to a Bot instead of failing silently. When you ask with `/ai` for something only the machine can tell, such as how much disk is left, the quick answer has no tools. Its model reaches for one and the call refuses it. Steve now makes the request an item, once, and a Bot does the work on a device. The reply in the thread says so, and the item reports its progress there. This applies only to trigger words you send yourself on your own account. When someone else uses your trigger word for such a request, the chat gets the short failure note described below. In your conversation in Steve and in chats a Bot answers, such a question still gets an answer that says why it can't be answered directly; "做成事项" turns it into an item as before. A chat where Steve may not start work, such as one with outside members, now says in its conversation why there is no answer and what to do instead. For a trigger word's answer, the next model in the list is no longer tried once a model reached for a tool. Every other model call, such as routing, mail triage and summaries, still tries the next model.

When a trigger word gets no answer, you can see why. The failure is recorded in that chat's conversation in Steve with the actual error, and a short note goes to the chat thread from your account ("这次没能处理…"). The note doesn't contain the details. When someone else used your trigger word, the note speaks as you ("抱歉，这次没能自动答上来，我看到后再回复你。"). Your account may be unable to send the note or the answer, for example because a permission is missing. Steve then tells you once, in the notifications and in your conversation, which account cannot send and that you can allow sending for it under Connections. It doesn't tell you again for every message. After your account sends again, you are told about the next failure. When the channel service refuses sending for good (a read-only connection), the card of the first refused message is that one notice, and no second one is added. Before, a trigger word that couldn't be routed, or that came from someone else on an account without permission to send as you, ended with no trace. It is now recorded in that chat's conversation too.

The Hub, its Nodes and the clients signed in to it are now managed in one place: **Devices**, with tabs for an overview, the Hub, the Nodes and the clients. What used to be **Settings → Hub** and **Settings → Access & clients** moved there (the old addresses lead to the new pages).

- **Hub**: the shared name and purpose (still editable by the instance owner only), version, address, Hub ID and the alias on this client; the computer it runs on with CPU load as a percentage of its cores, memory and free disk, and the way into its own Node; whether remote Nodes can connect, tailcat and the default upgrade policy; and how clients sign in, with single sign-on for the owner.
- **Clients**: this client, the other clients with the route each last came by, the ones not used for a week listed apart and those unused for 30 days flagged, signed-out ones folded away, and the access tokens with how many clients use each. Signing a client out asks first and can revoke the token it signed in with. On a Hub with several members the instance owner now sees and can sign out every member's clients; members still see only their own.
- **Nodes**: every Node with one plain status (fingerprint to confirm, offline, upgrading, upgrade failed, not taking new work, can upgrade, queued, online), its sessions and its version. A Node opens as a page instead of a dialog, where the owner can also stop or resume new work, rename it or unpair it.
- The overview starts with what needs you, then sessions, Nodes online, Nodes on the Hub's version and clients.
- The Hub switcher is shorter: the Hubs, then **Devices & connections**, **Add device…** (a Node, or a phone or browser by QR code) and **Add or manage Hubs…**. On a phone, **Me** has the same two rows.

- Scheduled work and other sessions that run as a workspace's service principal now use the harness's own sign-in on the device they run on, like everyone else's sessions there. Sign each harness in on the device with its own command (`codex login`, Claude Code's `/login`, Pi's `/login`, or a gateway and key helper in its own settings); nothing needs to be set up on the Hub. **Model access for service sessions** (Settings · Models) is gone: Steve no longer configures a model provider address or a vault key for a harness, and the old setting is removed on upgrade.
- There is only ever one sign-in per device. Codex and Pi sessions link to the device's own login file and Claude Code sessions use the device's own credential store, so nothing is copied and a refreshed token is written back to the device's sign-in instead of signing it out. With the sandbox on, a session of someone other than the device's owner may renew that sign-in but still sees nothing else in the owner's harness folders.
- Other people's and service sessions take only the sign-in entries of the device's harness settings (which provider or gateway, how the key is fetched), never the owner's personal instructions, skills, MCP servers or other settings. Whether the owner's own sessions load their personal configuration is still decided by the **Load the device owner's personal agent config** switch.
- When a harness is not signed in on any device that could run it, creating or running a schedule and opening a session are refused right away with a link to the Devices page, instead of asking you to configure a provider.

An accepted change in a project done by merging now actually lands. Steve used to ask the GitHub CLI for a repository field it does not have, so turning on auto-merge failed every time and the item stayed in its closing step. Steve no longer uses the host's auto-merge at all. It follows the pull request and merges it itself once every check passed, at exactly the accepted head (`gh pr merge --match-head-commit`), with the first merge method the repository allows. A delivery that was voided after its acceptance is therefore never merged. Steve also merges only when the accepted result is fully committed at that head: an accepted edit or new file left uncommitted goes back to the agent, so nothing is merged in part. If a delivery is voided while Steve's merge call is already running, the merge is still recorded on the timeline and in the statistics and becomes a card for you.

- Only a change an independent review passed is merged by Steve: the item's work graph had its required reviews succeed. Any other change that touched code waits on a new **PR awaiting merge** card. Only you can answer it, never YOLO. Approve it and Steve merges once the checks pass, or merge it on GitHub yourself: the item completes either way. Each such merge is recorded for the statistics with the review it had, so later reverts and fixes of unreviewed changes can be counted.
- A plan the agent reports while its result waits to close is recorded and no longer voids the delivery. Whether the result changed is decided by what the worktree holds and by new messages. An accepted result whose pull request is still open and already followed does not wake the agent again. A pull request that merged or closed for an earlier delivery does not count for the new one: the agent is woken and asked to open a new one, and no merge is recorded for it.
- A merge that fails is tried again later, with longer waits each time, and becomes a card for you after a few failures in a row. The same happens when GitHub cannot be asked several times in a row, and when the agent was already asked about its pull request many times in one cycle. A draft pull request, or one whose head is not the accepted commit, goes back to the agent with what to do.

- The statistics page has a **工作流** section: unit attempts and retries, the first-round review pass rate, sessions per item, the coordinator's token share and turn length, closings invalidated and deliveries refused by reason, accepted → merged time, channel reply time and session cold start. "Rework" is split into acceptance rework and unit retries, side by side, here and in the Bot comparison. The same figures are in `GET /api/stats/summary` under `workflow`.
- Steve now records closing invalidations, refused deliveries, pull request merges and coordinator wakes (with the unit, its status and attempt) as statistics marks, and when a session made its first tool call. Earlier invalidations and merges are taken over from item timelines once during the upgrade.
- `steve-hub --stats-snapshot --db <file>` prints these figures from a database file without a Hub, read-only, to take a baseline from a copy of an installation's database. See "Workflow statistics and a baseline" in `docs/deployment.md`.

对话 has a channel switcher: Steve, then each channel account you can see (the workspace's bots, and your own account for you alone), with how many of its conversations have new messages. Picking an account opens its groups and private chats, most recent first, each with the time of its last message and how many new messages came in since you last opened it there (counted back at most 7 days). The list can also be filtered by account.

A channel conversation now shows the chat's whole record, not only the messages Steve was handed: every message you may see, received and sent, in order, with earlier messages a page at a time. Under each received message it says what Steve did with it: answered, waiting for you (with a button to the card), handed off to an item (with a link to it), working, skipped or only recorded (with the reason it was recorded with), or failed with the reason, for example a trigger word whose answer could not start. A trigger word from your own account that was answered in your Steve conversation (because your account may not send as you) shows that answer's outcome, answered or failed with the reason, and links to it. A message Steve sent that did not go out says why, with a button to retry or discard it. A space where Steve never answered is listed too. Opening a conversation marks it read for you only.

- Devices backend: `GET /api/nodes` now says how each Node's link reached the Hub (`link`: local network, tailnet, internet or this machine, over TLS, a reverse proxy or tailcat, since when, and the latest round trip) and what machine it is (`host`: name, system and version, processor, cores and memory, reported by the Node itself). Both stay visible while a Node is away.
- The live event stream now tells a Node's owner whenever the Node changes (`node` events: linked or gone, paused, renamed, limit, upgrade phase…), so pages no longer need to poll.
- `GET /api/access` now marks each signed-in client `online` while it holds the live stream, with how many streams and since when, and names the access token it signed in with. The client's user is told when it comes and goes (`client` events).
- Signing a client out, or revoking the token it signed in with, now ends its open live stream at once; one revoked from the command line while the Hub runs loses it within 30 seconds.
- `GET /api/hub-metadata` lists the Hub's addresses (public, local network, tailnet, this machine).
- Nodes and the Hub speak protocol 0.7 (`node.host`); Nodes and Hubs of the previous release keep working together, without the machine description.

**Devices → Nodes** shows one card per Node, the Hub's own first. Each card shows:
- the computer it runs on;
- its status, and a plain line when something needs doing: an upgrade that failed and went back, a Node too old to upgrade from here, a Node behind the Hub, offline with its last error, or a fingerprint to confirm;
- CPU load, memory, the round trip to the Hub and its sessions, each with its last hour;
- what its agents are doing.

A Node's page is the same for the Hub's own Node and a paired one.
- **Now**: its figures, or its last data with a note while it is offline. Then its version, its running sessions (those waiting for your answer first, answerable from there) and the last 24 hours as charts.
- **Settings**: whether it takes new work, how many sessions it runs at once, its tags, personal agent config, its harnesses (the Hub's own Node), its identity and its project folders.

The **Version** card follows a Hub-managed upgrade step by step and quotes the Hub's real waits:
- what upgrading does, with **Upgrade to …** and **Upgrade now**;
- while it waits for running sessions, how many are left, with **Switch now**: that upgrade stops waiting and switches at once (the stopped sessions continue after the Node restarts);
- after a failure, the error, **Copy error** and **Try again**;
- for a Node that is upgraded on its own computer, the command to run there.

**Personal agent config** is now one default for the whole Hub, under **Devices → Hub → Defaults for every Node**, next to the default upgrade policy, because a Node serves every workspace. Each Node can still follow it or choose for itself. Upgrading starts the Hub's default as off if any workspace had turned the old workspace setting off; **Settings → Items** now links to the new place. API: `GET`/`PUT /api/node-context` (instance owner), `GET /api/nodes/upgrade-default` also returns `drain_secs` and `health_secs`, and `POST /api/nodes/{id}/upgrade/switch` (instance owner) makes the Node's upgrade under way switch now; it never starts another upgrade.
