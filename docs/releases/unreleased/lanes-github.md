- 合并通道：批准卡还没回答时到达的合并请求，直接并入这一批，批准卡换成一起列出它的新卡（加入前打开的旧卡不能再批准，你批准的总是实际要合并的那些），不再另开一批、等满 2 小时。项目页的合并通道可以看到在途和合批中的批次，能设置合批窗口和每批上限，并新增“立即合并发布”按钮，让正在合批的一批不再等窗口。
- 合并通道不再直接推送到托管方要求经 PR 或合并队列合入的分支（即使你有绕过规则的权限）：在出批准卡之前就会拦下，事项上出一张卡告诉你原因，不再退回给执行者重做（它改不了这条规则）；推送前还会再查一次。
- 合并通道里结束的批次（已发布、放弃发布、全部退出、发布并入下一批）会删掉它的临时工作目录和批次分支；发布失败等你重试时保留。
- 合并通道从来没有实际运行过“合并前检查”，项目页的文字改成“托管方要求的检查”，并说明每项交付时的构建和发布 tag 的 CI 是实际的把关。
- GitHub 仓库设置的“验收后”新增“直接开草稿 PR”：只对私有仓库生效，验收即视为同意，提交先过泄露检查（逐个提交检查新增内容和提交说明，后面的提交又删掉的机密也算；含二进制改动时也会问你），只推事项自己的分支，PR 一律开成草稿；验收时会向 GitHub 重新确认仓库现在仍是私有（关联后改成公开的仓库、查不到可见性时都按公开处理），公开仓库、泄露检查有发现、事项在 Node 上时仍会出卡片问你。合并仍然每次问你。
- 通过个人令牌（PAT）连接的仓库，开 PR 和评论的确认卡上会注明“以你的 GitHub 账号发出”。
- 合并通道按目标仓库和分支共用：项目页只列出你所在工作区的合并请求，其他工作区的只显示数量；通道里还有其他工作区的合并时，不能在这里改合批设置或立即合并。
- 目标分支要求经 PR 合入时，正在拦下的那一批不再收新到达的合并请求，新的请求进入下一批，不会卡在没有批准卡的批次里。
