- 你自己按“停止”中断的回合，现在会记在会话上：Hub 重启后仍然只给你一张“它停下了：你中断了这一回合”的卡，Steve 和 YOLO 都不会替你接着做；主控在收到工作单元未通过的提醒后被你中断，卡片会同时写明未通过的原因，也不消耗续跑次数。之前更早一回合的结束消息迟到，不会把这个权利冲掉；你发出新消息开始下一回合后，Steve 才会照常续跑。事项诊断里的工作状态新增“上一回合怎么结束、是不是你停的”。
- 暂停协作后马上恢复时，只有被暂停打断的那一回合算作暂停；恢复后的新回合被你停止，工作单元按你的停止处理，不会被自动续跑。
- 工作单元尝试次数用完后，它后面的评审、集成等单元不再一直显示“排队中”，主控会收到“某单元尝试次数已用完；受阻：……”的提醒。被取消的工作单元，它自己的事项会在回合结束后（或重启后的下一轮检查中）以“已取消”结束，不再一直留在执行中；未通过的单元仍按原样以失败结束，重试后旧尝试迟到的结束消息不会影响新尝试。
- YOLO 和 Steve 判断“需要你本人操作”时更准确：模型选中的选项本身（例如“用户已经在手机上确认过了”）也会被检查，不会代你提交；Agent 很长的最后一段回复里，开头的“请扫码授权，完成后告诉我”也不会因为只看结尾而漏掉；英文的 “Please log in to GitHub and tell me when done.” 这类登录请求同样留给你。只是讨论验证码有效期、OTP 位数、二维码组件这类设计问题，不再被误当成需要你本人操作，可以照常代答。
- 你按“停止”后，同一回合的结束消息在 Hub 重启后被再次送达，不会再把“你中断了这一回合”冲掉，也不会让 Steve 或 YOLO 接着做；你停的是新一回合时，上一回合迟到的结束消息不会占用这次停止，最终以你停的那一回合为准。停止请求没能确认送达（例如 Node 没有回应）时，仍按你停止处理，直到你发出新消息。
- 暂停协作后马上恢复、随后 Hub 重启，被暂停打断的那一回合迟到的结束消息仍算暂停，工作单元在原会话继续，不再显示“工作单元已中断”。
- 工作单元自己报告未通过后被重试，旧尝试迟到的结束消息会把旧子事项按“未通过”和原因关闭，不再显示为“已取消”；新尝试照常运行。
- 需要你本人操作的识别补上了“输入验证码后继续”和 “Use your passkey” 这类说法，Steve 和 YOLO 都留给你；介绍验证码流程、passkey 支持的汇报或设计问题照常处理。Agent 先请你扫码、随后用工具改走了无需授权的办法且之后没有再说话时，旧的扫码请求不再被当成它在等你。
