- 合并队列（试用，`STEVE_MQ=1` 开启，需要 Hub 自己的 Node）：合入和发布分开。
  - 按完成规则（合并或打 tag）结束的项目，验收通过的改动会自动进入目标分支的合并队列，不用 agent 再调用 `steve_publish`，也不再每批弹一张审批卡。验收时选“验收，先不合并”可以暂时留下，之后 agent 调用 `steve_publish` 再放进队列。
  - 每个目标第一次合入前问你一次是否允许；从旧的合并通道迁移过来的目标视为已经允许。目标分支要求 PR 或使用托管方的合并队列、或读不到它的保护规则时，队列不直接推送，这些事项按项目原来的方式合并。
  - 目标空闲就立即开始合入，忙的时候到达的改动自动攒成下一批，不再等 2 小时窗口。集成、检查和推送都在 Node 上 Steve 自己的镜像里进行，不碰你的仓库目录；构建输出在批次之间保留。
  - 与同一批前面的改动冲突、或迁移编号已被占用的改动会退回给 agent，并说明原因和下一个空号。只是 rebase、改动本身不变的话，不用重新验收，会自动重新进入队列。
  - 推送结果不明时先读远端核对，不会盲目重推；检查没有结果时开卡由你决定重跑、跳过检查还是退回。
  - 按 tag 发布的项目，合入后的改动进入发布列车：最早一件合入满 2 小时或攒满 10 件（可按目标调整）时关闭，只出一张发布卡，等你回答期间合入的改动并入同一趟、卡片原地更新。由 Node 在暂存区运行项目自己的 `ops/cut-release.py cut`。发布结果不明时按远端 tag 核对，已经发布的不会重复发布；发布失败的卡可以重试或放弃，放弃后这些改动随下一趟发布。
- 旧的合并通道（031）在开启合并队列后自动转换：排队中和等审批的请求重新排队，等发布的改动进入发布列车，原来的批次审批卡不再使用。
