- The Bot list shows each Bot as a card: its avatar, name and role, then its harness, model, running items and memories. Click the card to open the Bot. The switch and the ⋯ menu on the card still work on their own.
- A Bot's page opens on an Overview that is useful even when the Bot is idle. It shows who the Bot is, its last 30 days (turns, items done, first-pass rate, average time and cost per item, cache hit rate), its items with running ones first, and a summary of its capabilities, permissions, acceptance, system prompt and memories, each leading to the tab where you change it. A Bot that has done no work yet shows a short "Start configuring" guide instead.
- On the System prompt tab, "Tell Steve how to change it…" drafts a new version of the working rules or of your own prompt and shows it as a before/after diff. Nothing is saved until you press Apply. For integrations, `POST /api/config/draft` takes an optional `field` (`rules` or `prompt`) and `base` on a `bot` target, and the draft's `patch` carries the whole new text.
- In a Bot's Settings, the permission mode and the acceptance mode each choose from tiles with a plain-words description. The New Bot dialog uses the same tiles. In every mode, anything a Bot sends out through Steve (mail, GitHub actions) waits for your approval. The Memory tab uses the Knowledge page's memory panel, and the Schedules and flows tab lists the schedules the Bot runs.
- Codex Bots can pick a model before the Node has reported Codex's own list. Codex declares a built-in list (gpt-6.1-sol, gpt-6-sol, gpt-6-luna, gpt-5.6-luna), which is replaced by the adapter's report once the Node has probed it.
- **Capabilities** (能力) in the sidebar is the workspace's library of MCP servers, skills and remote agents. Each entry is defined once and chosen per Bot. The tabs are MCP servers, Skills and A2A, and every entry shows which Bots use it. A Bot's **Capabilities** tab lists what it uses: Steve · built-in first (always on, its tools folded inside with how often this Bot called each in the last 30 days), then its MCP servers, skills and remote agents, each with a switch for that Bot. **Add** picks one from the library or makes a new one. Editing an entry changes it for every Bot that uses it.
- MCP servers are a local command (stdio) or an HTTP or SSE endpoint, with environment variables or headers. A Bot's sessions get the servers it has switched on through ACP, next to Steve's own tools, the same way for every harness and Node. A change applies the next time a session's harness opens. A variable or header marked secret goes into the vault. It is never shown again, stored with the server, logged or put in the Node's command or journal, and the Node takes it from the Hub only when the harness opens.
- Skills are `SKILL.md` instructions, written where the Bot's harness reads skills before a session opens. An adapter declares whether and where it reads skills (`skills`); Claude Code and Codex do. A new skill can be filled in from a pasted `SKILL.md`.
- Remote agents (A2A) are added by their Agent Card address (a bare host is looked up at `/.well-known/agent-card.json`), and their name, description and skills are shown before you keep them. A key the agent needs goes into the vault. A Bot that uses one gets a tool, `steve_a2a_<name>`, that sends the agent a task and brings back its answer and artifacts. If the agent is still working after 100 seconds, the tool hands back the task id so the Bot can ask again later.
- Steve from outside: Claude Desktop, Cursor or another agent can connect to the Hub's `/mcp` with one of your access tokens (`Authorization: Bearer stt_…`), also from another machine. It gets the tools that need no Steve session: find and read items, hand Steve new work (`steve_item_create`), add to an item (`steve_item_supplement`), the knowledge base, your memories (read only) and the session list. **Capabilities · MCP servers** shows the address, makes a token (shown once) and gives a configuration to copy for a generic MCP client, Claude Desktop, Cursor and Claude Code.
- Steve as an A2A agent: its Agent Card is at `/.well-known/agent-card.json`, and `POST /a2a` with an access token takes `message/send` (a new task becomes an item, and a task id adds to that item), `tasks/get` and `tasks/cancel`.
- API: `/api/capabilities/{mcp-servers,skills,a2a-agents}` (with `POST …/a2a-agents/preview`), `GET /api/capabilities/steve`, `GET /api/bots/{id}/capabilities` and `PUT|DELETE /api/bots/{id}/capabilities/{mcp|skill|a2a}/{entry}`. Of the migrations that run on upgrade, 65 adds the library (`mcp_servers`, `skills`, `a2a_agents`, `bot_capabilities`) and drops the per-Bot tables that 62 and 63 create on the way. See "Capabilities" in `docs/deployment.md`.
- A Bot asked to release in a project without a release action gets an error telling it to deliver instead. Before, it waited for a release that never came.
