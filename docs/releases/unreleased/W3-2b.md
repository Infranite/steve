Needs a minor release: the Node journal moves to schema v4, which drops all earlier command, process and grant records and cannot be opened by an older Node.
Upgrading a Node deletes every command, process and grant record it kept from before the upgrade. Commands issued before the upgrade are refused afterwards (judged by the Node's clock, so a Hub whose clock runs ahead may see recent commands refused once); reading the output of an attempt that ran before the upgrade fails. Stop the old Node and its sessions before upgrading: the new Node no longer knows about processes the old one started.

A service Node now waits before migrating its journal until the old upgrade helper has committed the handoff, or the operation and service state prove that it cannot roll back. Claiming the handoff alone does not allow migration. If the helper has already decided to roll back, its stop signal interrupts the waiting Node while the old journal remains readable. Process inspection errors and uncertain helper ownership keep the Node waiting; elapsed time never proves that rollback is safe. On Linux the helper-absence fallback remains disabled pending native validation; a successful helper receipt still permits the normal upgrade.

The wait has no time limit, and the Node stays offline while waiting. For example, a Linux helper that dies after `linked` without writing its receipt, an unfinished `staging` or `switching` operation, conflicting operations, an unreadable record or an unknown phase can keep it waiting indefinitely. Even macOS inspection can remain inconclusive on a busy machine. Valid `staged` and `abandoned` records never started a helper and do not block the handoff; an older successful operation cannot override a current switch.

To diagnose a wait, find its operation ID in Devices and inspect that installation's `<node-home>/updates/node/<operation>.json` and `<node-home>/logs/node-upgrade-<operation>.log`. Include older attempts in `updates/node`: a conflicting or damaged record can belong to an operation other than the latest one shown in Devices. Check the filename against both operation fields, the requested build and phase, and `<node-home>/services/node.json` against the actual running executable. Do not treat the age of a record as proof that its helper exited, or collect full process arguments or environments into logs.

Before repairing a record, stop the waiting Node through its installation's service manager and preserve its home, identity, pairing and journal. Back up the exact operation record outside `updates/node`. Restore an unreadable or damaged record only from a verified copy for that same operation that reflects its actual state; never manufacture a `succeeded` receipt. For conflicting or obsolete records, a maintainer must first verify the specific operation's helper is absent, using its exact executable, installation home and user, and verify the service registration names the intended repaired build and its canonical executable. Only then move that operation's obsolete record out of `updates/node`, retaining the backup, and restart the repaired Node. Do not clear the whole directory or terminate processes by name. If ownership, process absence or the operation's outcome is uncertain, retain the record and keep the Node stopped for operation-specific repair. On Linux, a missing receipt still requires a repair build with validated native handoff inspection or maintainer-assisted recovery; removing a record merely to bypass the disabled check is unsafe.

After the handoff commits, a Node that cannot connect to the Hub stays on the new version. An upgrade shown as successful does not prove that the Node is connected. Recover forward by installing a repaired version that can read v4, preserving the Node home, identity, pairing and journal; do not reinstall an older version against that journal.

The Hub's own two Node journals are opened only after its upgrade startup gate commits. A verification failure before that gate opens leaves those journals untouched for rollback; after they have migrated, recovery likewise requires a version that can read v4.
