- 事项收尾时按事项自己的目标取证。Steve 读事项标题和每一版目标，目标要求的结果没有取得证据就不关闭：
  - 要求构建通过（“确认构建通过”“Release 构建”“CI 通过”等）：项目按“PR 合并并推送 tag”判完成时，tag 触发的 Release 构建成为收尾的必需操作，构建成功才关闭。构建失败，或 3 小时还没有结果，Steve 让 Agent 去修并通知你，事项不关闭。不打 tag 的项目以 Agent 交付里的构建检查为准。
  - 要求在本机生效（“当前实例”“本机生效”“部署到”“已上线”等）：Steve 自己的项目在 tag 推送后核对本机运行的版本是否包含它，没有包含就停在“等本机运行包含 vX 的版本”，并通知你一次；升级重启后 Steve 自动核对并关闭。其他项目由 Agent 在部署的地方实际核对。
  - 要求实际操作验证（“验证”“实测”“截图”“端到端”等）：`steve_deliver` 的检查项新增可选字段 `operated`，交付里至少要有一条通过并标了 `operated: true` 的检查（构建和测试不算），否则交付会被退回；交付里这条显示为“✓ 实际操作：…”。Agent 停下时远端已经合并打 tag，也不再只凭远端判完成，而是让它补上实际操作再交付。
  - 收尾阻塞项写明在等什么（例如“正在结束：等 Release 构建（v0.2.54）成功”）；Agent 开始工作时，协议里会写明这个事项要证明什么。本机 Node 上运行的会话和事项同样适用。
  - 你自己点「标记完成」就是证据，不受这些条件限制。识别靠关键词，可能多判或漏判：多判时直接标记完成；漏判时在目标里写明“确认构建通过”“在本机生效”“实际操作验证”这类字样。
