An accepted change in a project done by merging now actually lands. Steve used to ask the GitHub CLI for a repository field it does not have, so turning on auto-merge failed every time and the item stayed in its closing step. Steve no longer uses the host's auto-merge at all. It follows the pull request and merges it itself once every check passed, at exactly the accepted head (`gh pr merge --match-head-commit`), with the first merge method the repository allows. A delivery that was voided after its acceptance is therefore never merged. Steve also merges only when the accepted result is fully committed at that head: an accepted edit or new file left uncommitted goes back to the agent, so nothing is merged in part. If a delivery is voided while Steve's merge call is already running, the merge is still recorded on the timeline and in the statistics and becomes a card for you.

- Only a change an independent review passed is merged by Steve: the item's work graph had its required reviews succeed. Any other change that touched code waits on a new **PR awaiting merge** card. Only you can answer it, never YOLO. Approve it and Steve merges once the checks pass, or merge it on GitHub yourself: the item completes either way. Each such merge is recorded for the statistics with the review it had, so later reverts and fixes of unreviewed changes can be counted.
- A plan the agent reports while its result waits to close is recorded and no longer voids the delivery. Whether the result changed is decided by what the worktree holds and by new messages. An accepted result whose pull request is still open and already followed does not wake the agent again. A pull request that merged or closed for an earlier delivery does not count for the new one: the agent is woken and asked to open a new one, and no merge is recorded for it.
- A merge that fails is tried again later, with longer waits each time, and becomes a card for you after a few failures in a row. The same happens when GitHub cannot be asked several times in a row, and when the agent was already asked about its pull request many times in one cycle. A draft pull request, or one whose head is not the accepted commit, goes back to the agent with what to do.
