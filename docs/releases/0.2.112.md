# Steve v0.2.112

Bot 可用 `steve_deliver_file` 将文件或 ZIP HTML 包完整接收到 Hub，获得不可变版本的登录访问地址；`steve_deliver` 的文件产出复用同一链路。源目录清理、执行结束或 Node 离线后，已接收的文件仍保存在 Hub。

新增交付元数据、原文件下载、包内资源和独立分享授权接口。公开分享必须由用户另行授权并指定到期时间，可随时撤销；Bot 会话令牌不能创建分享。HTML 以静态沙箱展示，禁用脚本、表单、框架和外部连接。接收拒绝仓库元数据、依赖或构建目录中的输入，以及路径穿越、链接、超限 ZIP 和不完整或变化中的文件；每日备份包含交付对象。

事项产出和聊天文件卡片可打开、预览及下载 Hub 保存的文件，通过同事项、同工作区校验后的 `delivery_id` 关联不可变版本，旧路径和外站链接继续兼容。独立交付页面 URL 绑定所属工作区，支持切换工作区后的访问及登录回跳。Bot 返回的访问提示说明本机地址的可达性限制和 HTML 静态预览限制。

远程 Node 的交付按当前执行捕获的真实工作区解析绝对和相对路径，不再使用 Hub 的占位目录；`steve_deliver_file` 和 `steve_deliver` 的实际文件采用相同边界。越界、遍历、链接及过期执行被拒绝，旧 Node 需升级后使用。

A late model-discovery response can no longer restore stale readiness or models after a newer Node disconnect, probe failure or unavailable result. Reconnecting and refreshing discovery restores current models immediately; controlled installation keeps its existing protection against older probes.

Pi setup and session selection are now integrated across Devices, model selection and Bots. Refreshing setup keeps installation and disconnected states consistent with the model catalogue; verified external commands remain usable while unknown component integrity and other detected installations are explained separately. Ready components and provider-only failures no longer offer an ineffective installation action.

全局 Bot 和模型配置不再被 Hub 本机运行环境未安装或不可用的状态阻止；默认模型、手填模型和既有权限配置仍可编辑。页面注明本机状态与模型目录的来源，实际执行目标及权限由后端在启动时校验。提案无需运行环境在线；设备页的本机发现、安装和使用限制保持不变。

Global Bot and model configuration remains editable when the Hub's local runtime is missing or unavailable, including defaults, manual model IDs and existing permissions. Local status and catalog sources are labelled; the backend validates the execution target and permissions at startup. Proposals do not require an online runtime. Device-page discovery, installation and local-use restrictions are preserved.

Pi 的设备本机发现、受控安装和会话接入现已整合。全局 Bot、模型配置和提案保留默认或手填选项，不因 Hub 本机不可用而被阻止；实际执行目标仍由后端核验。本机已验证的 Pi 继续要求明确选择 FullAccess，thinking level 不作为权限模式。

Pi is now a built-in ACP harness with separate discovery of the official coding agent and its HTTP MCP-capable bridge. The instance owner can install both components asynchronously on the Hub's Node, follow missing, installing, failed or unknown states, and refresh discovery to select Pi without restarting. Installation uses Steve's own npm prefix, shares an exclusion lease with sessions and updates, preserves custom commands, and never adds Pi to an older installation in the background.

Configure Pi's model provider in the session's own state directory before use. Pi currently supports full-access sessions only: its thinking levels are not permission modes, and restricted modes are explicitly refused. The README and deployment guide describe Node/npm requirements, provider setup, retry and interrupted-install recovery, custom commands and separate Nodes.

Refreshing a disconnected Node also clears its previous ready state from session and model selectors. Reconnecting and refreshing restores availability immediately.

External executable adapters retain verified session availability even without the Node/npm used for managed installation. Component discovery distinguishes unknown package integrity from missing files and reports other PATH installations without changing the managed launch target. Installation acceptance also revokes older in-flight runtime and model probes, keeping subsequent Devices and state reads consistent while installation is running.

The installation and session flow now shares the native Pi SDK adapter and the current device page. Device identity, work status, live session limits and monitoring remain available alongside Pi component setup; native adapter modes and remote Node discovery are preserved.

Pi setup and managed execution retain unified live usage sampling and cancellation settlement. Adapter-prefix leases remain active alongside bounded process/transport cleanup, including isolated harness state directories.

- Devices and the runtime list now say "Not reported by the Node yet" in your language when the local Node has not answered, instead of showing the raw word "unknown".

The Hub no longer stalls its other work while sending a command to a Node waits for the database: when another process held SQLite's writer (a backup, a maintenance tool), the send loop could hold a runtime worker for the whole wait, so timers and requests elsewhere in the Hub paused with it and a request could fail with "database is locked" after five seconds.
