# Steve v0.2.114

A chat seen through several identities of the same platform is now one space with one copy of each message. This covers a Feishu bot and your own account through a channel plugin, or two people's accounts in the same group. Each message records which identities received it. Others in the workspace see what a bot received; only you see what reached your own account alone, also after a bot joins later. Where a bot is present, the bot answers and your account only listens. Two bots in one group still keep separate spaces and each answers for itself. Existing messages keep exactly the visibility they had.

An account's groups and private chats are grouped, so a long list stays readable: new ones first, with one action for all of them (record only, don't notify, or keep the default rules), then those with messages in the last 7 days, newest first; the others and the blocked ones fold. Past eight there is a search over the names. A group whose rules only act when you are @-mentioned now says so ("replies when @-mentioned; records the rest") instead of suggesting it replies to everything.

- Scheduled work and other service sessions can reach a model again. They run as the workspace's service principal and never use anyone's personal harness configuration or login, so a Codex or Claude Code session of a schedule used to fail with "Authentication required" and was tried again with every message. New setting: **Settings → Models → Model access for service sessions**, per harness a provider (or gateway) endpoint and a key from the shared vault. The Node writes the harness's own provider file into the service session's directory and hands it the key in that process's environment only; nothing of the owner's is copied.
- Steve now checks before it starts something whether its Bot can run at all: the harness is ready on the devices and, for service sessions, model access is configured. Creating, editing or enabling a schedule, and giving an item to another Bot, is refused with the reason and where to fix it; a schedule that fires while it cannot run makes no item and records the reason; an item gets one clear error instead of a session that fails and retries forever. Settings, the schedules page and the Devices page list the Bots that cannot run right now.
- A schedule starts no new run while the item of its previous run is still open: the fire is skipped, counted in the schedule's history, and noted on the open item ("上一次还没结束，跳过 <time> 的这一次"). A restart or a catch-up after downtime adds at most one row and no duplicate item, and nothing piles up for later. Schedules set to `overlap: run` keep running side by side.

- 我的发布: two files published within the same millisecond now list newest first in a stable order, instead of an order that could change between loads.

Trigger words (now `/ai` by default, besides `/bot`) work only on messages your own account receives; what a bot receives keeps the bot's own rules. The answer comes from your account in that chat, starting with `[AI]`, which the sending step adds, never the model. Where it goes is a setting: in the message's thread (the default; a quote reply in private chats), as a quote reply, or as a plain message. Nothing is answered once your account has left the chat. A conversation goes on without the word: your next message in the same thread, or a reply to the answer, is taken too and answered there. If the first one became an item, it goes to that item.

A new setting says who may use the words: only you (the default), anyone, or chosen contacts. When someone else asks for your personal details, the deployment or Steve itself, the request is politely declined and you get a notification. When it can't be told, the reply says to wait for you and you are notified.

Only the instruction decides whether a trigger word is answered or handed off as work, so a plain question gets an answer instead of an item. The answer knows the current date and time. Work handed off from your own trigger word is requested by you and runs as you. While it runs, a failure is reported in the thread straight away (at most every half hour for the same failure), and progress every half hour when it changed. When it ends, nothing is said: the message's reaction turns to done.

- A Bot whose harness only another device has is no longer refused with "not installed or not ready on the devices" while that device has just connected and has not reported its harnesses yet (for example right after the Hub restarts). Steve now says a harness is not ready only when every connected device, this machine's included, has reported and none has it ready; until then the session waits for the device, as it did before.
