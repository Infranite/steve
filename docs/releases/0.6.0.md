# Steve v0.6.0

Needs a minor release: offline management requires an existing database at this build's schema head; start or upgrade the Hub first when prompted.

Management commands (`steve-hub --access …`, including commands run by `steve setup`) use the running Hub through a private local Unix socket. Listing tokens and clients no longer reopens the database or competes with the Hub for a migration write lock. If the Hub is running or upgrading but its management socket is unavailable, the command reports the socket path and exits without reopening the database. When the Hub is stopped, commands take the instance lock and open only an existing database at this build’s schema head, without migrations, version-table writes, planner optimization or diagnostic recording. Older or incompatible schemas require starting or upgrading the Hub first. Offline token and client lists leave the database unchanged; token creation and revocation still write their records and audit entries. For supported schemas, existing command output and exit codes are unchanged.

Needs a minor release: Hub backup names and layout have changed; update tools that consume the old flat backup filenames.

Hub daily, upgrade, repair, cleanup and manual backups now use a single verified SQLite snapshot implementation. Each backup lives in a `<reason>-<UTC time>-<id>/` directory with `manifest.json`, the database and optional `files.tar`. The manifest records checksums, the snapshot's schema and whether the best-effort files archive is complete. The Hub no longer creates flat `daily-*.sqlite3` files.

Owners can request a diagnostic backup with `POST /api/system/backup` or `steve-hub --admin backup`; the CLI uses the private management socket, or takes the installation lock when the Hub is stopped. `--reason pre-upgrade` selects upgrade retention; `--reason pre-destructive` records a retained backup before a manual destructive operation. Status includes counts and bytes by purpose. Daily copies are kept for 14 days and upgrade copies for eight backups; diagnostic and pre-destructive copies are retained.

To restore manually, stop the Hub, remove the old database's `-wal` and `-shm` sidecars, and copy the database named in the chosen manifest to `data/steve.sqlite3`; provide any required external vault keys separately.

Installers, source deployments, development snapshots and delivery-repair scripts now request backups through `steve-hub --admin backup`. Deployment receipts name the manifest directory, and failed backup commands stop deployment. Legacy flat backups are left untouched. Source installations use the Hub's daily scheduler; the separate backup launchd script and plist have been removed. Unload an existing backup job and remove its plist as described in the deployment guide.

The shared files archive includes `deliveries` as well as attachments, workspace outputs, signing identity, secrets and `steve.env`; its completeness is recorded in the manifest. Delivery-repair scripts use the retained `pre-destructive` purpose.

Hub no longer adapts to older remote Nodes; upgrade remote Nodes together with the Hub (Devices → Upgrade). A Node that has not been upgraded may answer newer requests with an error until it is.

Needs a minor release: legacy ACP transcript rows and Hub-side local-file fallbacks are no longer supported.

Local harness history is discovered and imported through the local jobs Node, including when `STEVE_NODE_MODE=off` disables local session execution. The Hub no longer scans harness history files itself. Import keys must appear in the Node’s discovery results. An inert `STEVE_NO_RESUME=1` copy has no history Node and returns `503` with code `unavailable` for history listing and import.

Transcript reads accept `steve.v1` rows directly. Older ACP rows and unknown formats appear as an unsupported-format system entry; they are not converted. All transcript requests use the same bounded pages (at most 500 rows and a 2 MiB payload budget, with a single oversized row allowed), so callers continue from the last sequence until an empty page.

Delivery source files, including Hub-owned item outputs, are read through a Node. A missing delivery Node now fails the transfer instead of falling back to a Hub-side file read.

Needs a minor release: removed STEVE_* variables are now rejected by --check-config and startup

Remove `STEVE_ITEM_PREFIX` from the Hub environment before upgrading, including empty assignments.
Set item prefixes in workspace settings instead. The Hub now rejects invalid flags, takeover
counters, idle-release values, disk-policy values and HTTP(S) URLs instead of silently keeping
defaults. Boolean flags use `0`/`1`; backups use `on`/`off`.

The Hub and authentication share one secret-file reader. OIDC accepts either
`STEVE_OIDC_CLIENT_SECRET` or `STEVE_OIDC_CLIENT_SECRET_FILE`; setting both is an error.
OpenViking accepts only `STEVE_OPENVIKING_KEY_FILE`, never the direct root-key variable.
Addresses and origins use direct values, without file-source variants. `STEVE_PORT` must be
a nonempty decimal integer from 0 to 65535.

Secret files must be regular UTF-8 files with Unix permissions no broader than `0600`.
Special files are rejected before open; permissions are checked on the opened handle.
Correct existing OIDC/OpenViking file permissions before upgrading. Only final CR/LF are
removed; spaces remain part of file-based secrets. Configured sources are validated even
when an optional backend is off. Credentials loaded by CLI, vault and connectors keep their
existing contracts.

Storage retention now runs in short background slices, including when the Hub is started with `STEVE_NO_RESUME=1`. Expired feed and attention pagination capabilities are removed by background retention instead of during read requests; expired capabilities are still rejected immediately. Node vitals, session turn projections, and tool usage are also cleaned in the background. Diagnostic byte limits remain hard limits: critical facts can evict their item's oldest diagnostic records, while background cleanup keeps space below the total limit. Archived session payload compression continues to use Core's existing retention settings and busy-session protection.

Hub 后台任务统一名称和停止句柄，并记录运行次数及耗时。实际安装的维护任务是 core.housekeeping 与 core.releases。模块和 Node 协调器共用可注入时钟，持久化期限仍使用 Unix 毫秒。

生产路径的 core.housekeeping、core.releases 和 library.sweep 统一使用 every，每次检查分别记录运行次数与耗时；错过周期后不集中补跑。

后台任务 panic 会记录任务名、错误日志和 steve_job_panics_total 指标。自动升级检查与签名迁移也纳入命名任务；Hub 停止时会停止所有自有后台任务，包括未提供任务袋的扩展领域。

Errors can carry stable reason codes, which the web client uses to display translated messages with a safe-detail fallback.

An `outcome_unknown` error that carries no explicit retry is now marked `never` instead of `now`: the operation may already have taken effect, so a client checks its state rather than resending it.

Queued channel sends and personal notifications wake after their database changes
commit, with a shared recovery fallback. Unknown notification topics and deferred
sends no longer keep the queue busy or hold back other due work. Provider retry
limits, retry hints, authorization checks and rate limits retain their behavior.

Approved sends now wait for the latest linked personal-notification attempt deadline
before becoming eligible, rather than using that deadline only to order the queue.
This usually adds about ten seconds when a notification attempt is pending.

Needs a minor release: invalid stored flows may now be disabled or failed instead of silently retried; repair and re-enable affected schedules or retry failed runs.

Flow waits and failed-run retries wake at their own deadlines instead of waiting up to 15 seconds for a trigger poll. Committed todo changes immediately replan reminders, and deferred alarms no longer crowd due reminders out of a batch.

A local claim or planning error now ends only the affected record: its trigger is disabled, its run fails, or its reminder/request is cancelled. The failure is recorded in the audit log. Other due work continues on time; a failed reminder cannot undo other reminders in its batch. Repair the subject, then resave/re-enable its schedule, explicitly retry the failed run, or re-arm a cancelled reminder. Action-execution retries retain their existing policy.

Stored graphs that cannot be parsed permanently disable their triggers. Invalid persisted wait or retry state fails its run instead of being skipped. Planning errors with a 4xx status cancel that subject's planned alarms. Where a stored time zone needs a fallback, the operator's system zone is used rather than Taipei.

Cron evaluation uses the shared runtime implementation and RFC 5545 time-zone rules: a time in a spring-forward gap is shifted using the pre-transition offset, and a repeated fall-back time runs on its first occurrence only.

`steve-hub` now refuses arguments it does not recognise (exit status 2) instead of starting a Hub with them; run it without arguments to start the Hub.

The Node now writes its journal in batches (at most 200 ms apart) instead of once per event, cutting its disk writes by about a third under load.

Needs a minor release: a Node replaces its journal from an earlier version instead of migrating it, and an older Node cannot open the new one.

Stop the old Node and its sessions before upgrading. The new Node refuses to start while any process group recorded by the old one is still alive; once they are gone it starts a fresh journal. Everything the old journal held is dropped, including events the Hub had not yet acknowledged, and commands issued before the upgrade are refused afterwards (judged by the Node's clock, so a Hub whose clock runs ahead may see a recent command refused once). Reading the output of an attempt that ran before the upgrade fails. There is no way back to the previous version.

Needs a minor release: the installation CLI honors STEVE_HOME and service actions require a matching registration

Before upgrading, check that each installation has `services/hub.json` or
`services/node.json` in its home. If that registration is missing, rerun
`steve setup hub` or `steve setup node` for the original home and service label
before using start, stop, restart or uninstall. Use `--home` and `--label` for
custom installations. There is no fallback for installations without a registration.

Previously, the installation CLI ignored `STEVE_HOME` when `--home` was omitted.
With the real account's `HOME`, `steve hub stop` selected `$HOME/.steve` and
stopped the Hub installed there, including a production Hub, even when
`STEVE_HOME` pointed to a different installation. On macOS, launchd's `bootout`
targets the account's GUI domain and service label, so changing the intended installation home alone did not isolate it.

The installation CLI now selects its home from `--home`, then `STEVE_HOME`, then
`$HOME/.steve` (Hub) or `$HOME/.steve-node` (Node), including setup and reconfiguration.
Start, stop, restart and uninstall require that home's own service registration
with the matching component and label before contacting launchd or systemd.
`STEVE_HOME` is shared by both roles; select the Node's home explicitly when needed.
An interrupted setup that has not registered a service can still be set aside
with `steve setup --fresh`; it skips service operations and preserves the old home.

Digest Bots now start when packet-count or packet-age thresholds are met, and expired packet leases are recovered at their deadline instead of waiting for the next minute. A schedule that cannot start records a failed run and retries after a minute without delaying other workspaces. Consecutive startup failures with the same error share one run record instead of filling the run history. Schedule run responses include the startup failure count, and a changed error starts a separate record.

The Hub now shares process-local, weighted caches for statistics, allowed client origins,
runtime and Node harness observations, MCP tool lists, and GitHub repository lists and ETag
bodies. Committed changes synchronously invalidate their dependencies before the next read.
Connection lifecycle, readiness evidence and in-memory projections remain independent of
optional caching.

`STEVE_CACHE=memory` is the default; `STEVE_CACHE=off` bypasses these shared caches for diagnosis.
`STEVE_CACHE_MEMORY_MB` sets the total memory budget (default 256, a positive integer), split
between registered spaces. Other backends, including Redis and plugins, are unsupported in
this version. Entries use estimated byte weights; no external cache service is required.

A single cache registry is injected from Hub startup. Runtime and Node reports have no
separate display copy. Runtime, Node and MCP displays have bounded stale grace; eviction or
expiry beyond that grace leaves a cold view until discovery completes. Model selection and
dispatch read the same recent report, never stale display evidence.
MCP listing failures pause retries for 60 seconds in their own bounded space.

Scheduled YOLO actions now follow their saved deadlines, including when storage reads are delayed, and wake their runner after schedule changes commit. A failed action keeps its own 15-second retry, so other actions can run on time; repeated executor errors still trip the existing circuit breaker.

Connection token refresh, health checks and directory sync now follow their next deadlines, including existing health backoff, daily workspace time zones, catch-up and event debounce. Periodic reconciliation no longer replays missed scans in a burst. Folder scan requests leave the full-scan deadline unchanged, and judging still re-reads its configured delay after each pass finishes.

Connection health, vault access, merge, judge and YOLO session-error retries use the shared backoff policy with the same waiting sequences and caps. Profile lookups retain their existing 1/6/24/72-hour schedule.

Token refresh now runs at the saved expiry minus 10 minutes instead of waiting for the next 5-minute polling tick. New connections are discovered by the deadline loops within their 60-second fallback; connection writes do not currently signal these loops. If an individual directory connection lookup fails, its pending request is retained for a retry 15 minutes later while other requests continue; previously a failed tick could discard all pending requests in that batch.

Scheduled YOLO changes wake their runner only after the outermost transaction commits, including writes outside the ledger helpers. Retrying an action retains its original business reason. During maintenance the runner rechecks within the existing 15-second cadence.

Needs a minor release: the manual item-category backfill and category-review APIs have been removed.

The Hub no longer runs the one-time item-category backfill at startup. The historical-item check and review controls have been removed from tag management, along with POST /tags/kinds/backfill and GET/POST /tags/kinds/review. New task items still receive exactly one category through the normal write paths. No database migration or historical data conversion is performed.

GitHub analysis reports are created with exactly one documentation category. Task creation now refuses missing or ambiguous categories at the store write boundary.

Needs a minor release: upgrade the Hub and all Nodes together; ordinary Node links now require exactly the same integer protocol number. Remote Nodes using the former 0.x protocol do not understand the new upgrade channel and need one manual upgrade first, using the stopped-service `steve node doctor`, `stop`, `update --release <new-bundle>`, and `start` procedure in `docs/deployment.md`.

After that first migration, a protocol mismatch keeps an authenticated upgrade-only connection open. Devices shows that an upgrade is required, and the existing upgrade action uses a separate permanent v1 protocol. Ordinary work, events, tools, secrets and uploads cannot cross that connection. Upgrade switches to an older release are refused because an older Node may not read a newer journal.

Queued work remains pending while a Node reconnects in upgrade-only mode and resumes with the same operation IDs after a compatible reconnect. Devices distinguishes an older Hub from an older Node. Upgrade discovery uses only `probe_build`; ordinary capability responses no longer duplicate the release build and upgrade feature.

Upgrade protocol selection lets a newer Hub retain support for older Nodes. Archive reads use operation-scoped `upgrade_fetch` with receiver-sized chunks, and a Node without a shared upgrade protocol reports that the Hub needs upgrading. Pause state is reapplied after an ordinary reconnect.

Needs a minor release: single-user read visibility now includes objects previously hidden by member visibility rules.

In single-user installations, objects created as private by another member, or restricted to a team, space, or another connected account, now appear in the owner's reads. Workspace isolation, message identity records, personal sending permissions and authorization grants remain enforced. Across all reads governed by viewer visibility, service principals and callers without an identity can access only workspace-level objects, including contacts, people, teams, accounts, memories, signals and knowledge folders. They cannot read private objects they created themselves, such as private memory candidates proposed by a service session.

Needs a minor release: category initialization now refuses legacy tags whose reserved category name is used in another tag category.

Before upgrading, rename any non-category tag named bug, feat, doc, refactor, ops or chore. Initialization reports a conflict instead of changing that tag's category and silently adding another category to its items. A refused category initialization leaves the existing tags and items unchanged. If this conflict is in the default workspace, the Hub fails to start; in any affected workspace, task creation, task tag changes and creation of any tag are refused until the conflict is resolved. The error identifies the tag ID, name and current category and asks you to rename it and retry, or rename it offline and restart if the Hub cannot start.

Workflow child creation validates inherited tags through the same single-category check as ordinary task creation. An invalid parent category set must be corrected before dispatch; refusal does not create a child or consume its item number. No historical category backfill is performed.

While the Hub is running, rename the conflicting tag through the existing tag editor or API and retry; no restart is needed. If the Hub cannot start, recover offline:

1. Stop the Hub and its service manager with `steve hub stop`, using this installation's existing `--home` and `--label`. Keep all writers stopped during the repair.
2. Open the configured home's `data/steve.sqlite3` with `sqlite3`. Use `.backup '/path/to/new-offline-backup.sqlite3'` to create a backup at a new destination before changing anything.
3. Use the tag ID, name and current category from the error. Pick a new name that is unique within its workspace and is not bug, feat, doc, refactor, ops or chore (for example, legacy-chore). Run the following interactively, replacing the placeholders with those values; escape a single quote inside a value by doubling it:

   ```sql
   BEGIN IMMEDIATE;
   SELECT id, workspace_id, name, cat FROM tags WHERE id = '<reported-id>';
   UPDATE tags SET name = '<new-name>'
   WHERE id = '<reported-id>' AND name = '<reported-name>' AND cat = '<reported-category>';
   SELECT changes();
   ```

4. Commit with `COMMIT;` only after checking that the selected row is the intended tag and `changes()` is 1; otherwise use `ROLLBACK;`. Quit SQLite and restart the Hub. If another conflict is reported, repeat for that tag. This renames the existing tag without changing its ID, category or item associations; it does not reclassify historical items.

The upgrade supervisor now finishes process-group cleanup before reaping the Hub child, so repeated shutdown cannot signal a reused process-group number. Forced shutdown signals both the recorded group and the Hub child, even if their group membership changed.

每日备份可在设置页开启或关闭，并选择保留天数，默认开启、保留 7 天。关闭后停止生成新日备份，已有日备份仍按所选期限清理，最新一份保留。安装运行配置仍可停用自动备份。升级前、破坏性操作前、手动和诊断备份不受每日开关影响。

网页立即备份和默认管理命令创建的手动备份不会自动删除，也不占用自动备份的容量额度；状态单独报告手动备份用量和最近一轮清理失败数。每日、升级前、破坏性操作前和诊断备份统一由后台按用途清理，内部容量保护会优先删除最旧的可清理副本，各用途最新一份始终保留；受保护副本造成超限时状态可见。诊断备份只复制数据库，其他用途按统一规则附带文件。以 STEVE_NO_RESUME 运行的数据副本不清理备份目录。

Built-in delivery tags are created only when a workspace is first created, including the initial default workspace. Deleted or renamed delivery tags are not recreated by startup, task creation or later tag changes. An existing workspace without them is left unchanged. New tasks and new outputs can still use delivery tags that remain available; ordinary tags of the same name are left in their chosen category and are never attached automatically as delivery tags.

Initialization no longer moves nonstandard tags from the type category into the topic category or infers delivery tags from historical item titles, goals or artifacts. Existing item tags are left unchanged. The obsolete delivery-backfill checkpoint setting is deleted at startup and is no longer hidden by a special settings filter. No manual upgrade action is needed.

Tags in the 类型 category with nonreserved names now remain ordinary tags when displayed, sorted, edited or switching an item’s kind.

IMAP synchronization now reports rejected UID SEARCH commands as errors and keeps the unconfirmed window for retry, instead of treating rejection as an empty mailbox and permanently skipping messages. A server that rejects SEARCH SINCE is reported as an error; Steve does not fall back to scanning the entire mailbox. Message-ID lookups also report search rejection instead of saying the original message is gone. Previously advanced cursors are not reset, and mail skipped by earlier versions is not backfilled. A rejected folder no longer blocks the other folders on the connection; errors identify the folder and IMAP command. Missing or zero UIDVALIDITY is treated as a connection failure and preserves the saved cursor. If a folder keeps rejecting requests, each round still ends in error and uses the existing retry backoff (up to five minutes), rather than the normal two-minute poll. Other folders continue to advance, and IDLE can still wake the runner early.

Digest queue-triggered schedules stop retrying after three startup failures in the same configuration. Any save of the bound schedule or Bot opens a new retry budget, including a name-only edit or disabling and re-enabling it. A bad schedule is isolated from other workspaces, and ordinary scheduled or manual runs stay enabled.

Recognizable digest startup-error markers created by unpublished development builds are removed on startup, along with their steps, waits and run links. Independent items and child runs are retained. Current startup failure history and retry budgets are kept.

Startup rejections show a stable explanation rather than database decoder details; the original error is logged. If startup tracking metadata is damaged, the digest owner can read its code and flow/run location in the diagnostics field of GET /api/digest/bot.

Saving the schedule or Bot also recovers when an older startup budget is damaged. The old record stays available in owner diagnostics, even after a new run starts. Repeated wakeups log a damaged run once per Bot worker lifetime.

IMAP folders that report untagged warnings such as `* NO [UIDNOTSTICKY]` can now sync normally. Mailbox selection for syncing, finding originals and watching the inbox waits for its own tagged completion: untagged NO/BAD responses are logged as warnings, while matching tagged NO/BAD responses remain refusals. Incomplete responses and missing or zero UIDVALIDITY remain transient failures and do not reset or advance saved cursors. Existing sync windows and historical cursors are unchanged.

Needs a minor release: custom clients using user-scoped device notifications must treat node and client events as Hub-wide notifications.

On a single-user Hub, node and client SSE notifications now reach all connected workspaces. The shared Scope type now contains only Ws and Hub; the User variant is removed. Event payloads still include the user field. The web client uses the updated generated types. Signing a client out still closes only that client's streams, and client presence notifications still leave the state cache valid.

Schedule startup failures now store a stable error code and parameters, so changing language does not split repeated failures or reset their budget. Run history and the latest-run summary are translated in the reader's current language.

Startup diagnostics distinguish damage that still blocks the current configuration, historical damage after a configuration save, and records whose source cannot be identified. Historical records no longer keep telling you to edit an already changed configuration.

On startup, old digest startup-failure markers that stored translated text are deleted together with dependent steps, waits and links. Independent items and child runs are kept; references to deleted runs are cleared. Old failure counts are not converted or backfilled, so affected configurations start a new bounded retry budget. Ordinary run history and successful startup anchors are kept.

Plugin subscriptions to `event` now receive the same slimmed transcript payloads as SSE.
