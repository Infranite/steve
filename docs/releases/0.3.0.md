# Steve v0.3.0

The macOS client now has a native toolbar showing the current Hub, page and confirmed selected workspace, with Hub controls, connection details and an Attention entry point. Its menu-bar panel emphasizes context and navigation instead of operational counters. Native Settings and a Navigate menu accompany a single restorable main window: closing it keeps the menu-bar client running, and quitting the client does not stop the Hub. Pairing links still require native confirmation.

An additive bridge v2 carries page metadata and acknowledged, Hub/workspace-scoped navigation. Only an explicitly opted-in macOS shell hides the duplicate web Hub switcher; browser, older-native and iOS navigation remain available. Navigation errors are visible, and unsupported deep targets fail rather than claiming success. Native Hub switching waits for the current page to approve leaving; unsaved edits and in-flight writes also block workspace-scoped navigation before any workspace change. Missing or stale page approvals never switch the Hub.

This is the shell foundation, not background reminder delivery. Attention separately labels Steve replies, pending work, completions/deliveries and connected-channel messages as unavailable until their personal reminder data is connected. It shows no invented unread counts, requests no notification permission and delivers no background notifications.

The macOS client now monitors personal attention for the confirmed account and selected workspace independently of its web window. The toolbar and menu bar keep Steve replies (messages), pending work (cards), completions/deliveries (entries) and channel messages (conversations) separate; unavailable, stale and sign-in-required states are not shown as zero. A Dock dot indicates attention without adding incompatible counts together.

The compact native titlebar shows the page and workspace once, keeps Hub switching secondary, and uses the web page's actual background and light/dark appearance. Decorative toolbar capsules and duplicate system titles no longer squeeze the current context; Hub connection details remain available behind a quiet status indicator. Native menus, attention panels, Settings and new notification text follow the page's Chinese or English UI selection; closing the main window retains the last confirmed UI language. Stored user Hub aliases are not translated.

System notifications are off by default. Enable them in native Settings and use the explicit permission button to ask macOS for access. Category toggles, category-only privacy previews, sound and per-conversation local overrides are available; channel notifications otherwise follow the Hub's notification setting, and quiet is not mute. These local controls do not change server read or mute state. The app respects system notification settings and does not request critical or time-sensitive delivery.

The first successful snapshot silently establishes a baseline. Native-scoped persistent event checkpoints prevent reconnect/relaunch replay; invalid or full deduplication storage pauses banners instead of forgetting history. Logout, profile removal and account changes remove the affected local records and delivered notifications. Closing the main window keeps monitoring the last confirmed workspace; quitting the client stops monitoring without stopping the Hub.

Notifications contain only scoped identifiers and generic/category text, not message bodies or credentials. Opening one restores the main window, verifies the native account, selects the Hub/workspace and opens the actual reply, decision, expanded delivery entry or channel conversation. Foreground suppression applies only to matching entities actually visible in the focused current document, not to an entire page. Older Hubs without the personal-attention API remain explicitly unsupported.

Personal attention is separated into final Steve replies, actionable cards, completion/report Feed entries, and connected conversations, with caller/workspace-scoped snapshots for desktop clients. Final replies gain personal, monotonic reading state without treating streamed drafts as new messages. Existing Feed and channel reading remain separate, and unavailable sources are not reported as zero.

Needs a minor release: STEVE_WORKFLOW_MAX_PARALLEL changes from a Hub-wide collaboration limit to a per-root-item-tree limit.

协作并发不再让无关事项争抢全局默认四个名额。每个根事项及其所有层级的派生事项共享自己的协作额度，默认仍为 4；工作图的 `max_parallel` 只能进一步收紧当前图，不能给子事项重新分配额度。

升级后多个根事项可以同时执行超过四个协作单元，所有实际执行仍受所在 Node 的会话容量限制（默认 32）。运维应按机器资源设置 Node 容量；原 `STEVE_WORKFLOW_MAX_PARALLEL` 配置会保留数值，但不再限制整台 Hub 的总并发。暂停或结束中的执行在确认停止前仍保留占位，损坏的事项父链不会获得新的额度。本次不开放工作单元再建嵌套工作图。

**Devices → Overview** starts with what wants you, one line each with its next step:
- a Node to confirm (**Confirm** opens its fingerprint check);
- an upgrade that failed and went back;
- an upgrade under way;
- a Node behind the Hub (with **Upgrade**);
- a Node offline, with the first words of its last error;
- sessions waiting for your answer.

Under it are four numbers: sessions running against the total limit, Nodes online, Nodes on the Hub's version and clients online.

Then a **connection map**:
- The clients on the left, the Hub and its own Node in one frame for the computer they share, and the remote Nodes on the right.
- Lines from the Hub to a Node show its state by color and by line style. They get thicker with its sessions and move while sessions run, and they are labelled with the route (this machine, LAN, tailnet, tailcat, HTTPS) once the Hub reports it.
- Pointing at a card or focusing it shows its facts and lights its own line. Arrow keys move within a column, and a click opens the Hub, the Node or the client's row.
- Seven or more Nodes take one line each and more than twelve fold into "N more". With no other computer, a card explains when to add one.
- On a phone the map is a tree. **Show clients** turns the client column off and is remembered.

**Add device** is now one dialog for both kinds, step by step. It replaces the separate Node pairing dialog, the client QR dialog and the tailcat section.
- For a **Node**, choose how it reaches the Hub: the same network or HTTPS, tailcat (the owner can turn it on right there) or a remote install. Then copy the command and the pairing code, wait for it to connect and check its fingerprint.
- The fingerprint is checked in full. Paste what the Node printed, or type its eight groups; each group is checked as you go, and the Node can be added only when all eight match. **They differ, reject** unpairs it and makes a new code. A check of two random groups was considered and rejected as weaker: someone who knows a Node's key can make another key that matches two given groups.
- For a **client**, it shows the QR code as before.

`steve-node pair`, `status` and `rotate` print the fingerprint in groups of four.

The devices pages now update as soon as the Hub reports that a Node or a client changed, instead of waiting for the next 10-second read.

Opening Chat’s History or Items panel no longer continuously resizes the conversation during its animation. Panels remain docked beside the chat, with an animated reveal, reduced-motion support, keyboard focus restoration, and safe cleanup when switching quickly between panels.

Needs a minor release: dynamic workflows now default off; operators wishing to retain multi-Bot orchestration must explicitly set `STEVE_DYNAMIC_WORKFLOWS=1` and restart the Hub.

Ordinary tasks execute in the current responsible Bot session without extra settings. Disabled workflows cannot be planned, retried, resumed or start new child turns, including through cached tools or queued prompts. Existing in-flight work can settle, and stop reconciliation, results, history and acceptance safeguards remain available.

Existing unfinished graphs are not automatically accepted or converted. Pause them, wait for confirmed settlement, then explicitly confirm single-session takeover on the item page if desired. The confirmation records that required graph review/integration acceptance is waived; earlier review defects still need fixing and ordinary PRs still require human review. The existing panel explains the disabled state and keeps safe recovery actions available.

- Devices · Hub lists every address the Hub answers on (public, local network, tailnet), each with its kind, instead of only the one this client uses.
- Devices · Clients marks the clients that hold a live connection to the Hub now as online; the page head counts the clients online, and the Clients tab counts this browser too when its sign-in is not a registered client.
- A Node's page keeps the details of what changing its session limit does in a tip beside the limit that opens on a click or a tap (so it reads on a phone too), and its CPU figure says the load is a one-minute average.
- With much larger text, the Hub's name editor keeps its hint and counter lines from overlapping.

- Installing a Node remotely over tailcat (Devices → Install remotely) now pairs. `steve setup node` passes the pairing code it was given in `STEVE_PAIR_CODE` on to the pairing. Before, the code was lost, and the install ended with "no pairing code".
- The install dialog now shows real progress: bytes downloaded and the speed, then the check of the installer; bytes sent to the target; and on the target, the install, pairing, adapters and service start. Each step shows how long it took, and a running step shows a live clock. The progress is kept by the Hub, so a page opened later shows the same install.
- An installer the Hub downloaded before is reused for the next install of the same version and platform. It is checked against the release's manifest again, and the Hub keeps the two most recently used. The cache is under `<STEVE_HOME>/tailcat/installs/cache`.
- A step that gets no data fails with a reason instead of hanging: 60 s with nothing downloaded, sent or answered, or 10 minutes with no output from the setup on the target.
- A failed install shows the step it failed at, after how long, and why, with a retry button. The address stays filled in. Starting a second install to an address that is already being installed shows the running one instead of starting it again.
- `GET /api/nodes/installs` lists your remote installs, newest first. Each step now has `kind`, `ended`, `elapsed_ms` and `progress`, and the install has `failed_step` and `address`.
- A Node home left by a setup whose pairing never made the Node's key, as a failed remote install leaves one, no longer blocks the next setup. Before, a newer release refused it as another version's installation, and another Hub refused it as a pairing sent elsewhere. Setup now continues it and drops the old Hub's pin. A home with a Node key or a registered service is still protected.

- A disclosure check whose model gave no answer (it timed out, failed or answered something unreadable) is no longer shown as a possible leak. The reply's basis says `unchecked` and names every model tried, and the card says "检查没跑完：…" with what happened instead of "可能泄露". Such a reply is still never sent without you: it waits for your approval, and YOLO does not send it ("披露检查没跑完，不自动发"). A GitHub comment whose check did not finish is not posted under a grant either.
- On your own chat account a draft no longer waits for the check model before its card opens. The card opens at once with "（披露检查还在跑）", the check runs afterwards (up to 60 seconds, and once more on the gateway's smart tier if the first try fails) and the card then shows what it found. YOLO waits for the result. If you approve or discard the draft first, its basis says the check did not finish.
- The check now reads the conversation the people in the chat can already see, not only the message being answered. It also knows the samples of how you talk that the drafter was shown: copying their content into a reply is flagged, and their tone is not.
- A rewrite of a flagged reply may only delete the flagged parts. A rewrite that adds words is thrown away and the original stays as it was, flagged, for you to look at. So is a rewrite that leaves only hedges such as "这个还不好说": it is not sent in place of the reply. Only when the rewrite leaves no text at all is there nothing to say: the reply is dropped, its card closes saying why, and a bot reply dropped this way is recorded in the audit log. A rewrite that leaves a plain answer such as "没有" or "确定" is an answer and is checked again like any other.

- Todos (我的待办) are now every member's own, not only the workspace owner's: each member lists, adds, changes and undoes their own todos through `/api/digest/todos`, and nobody sees another member's. The matter page shows only your own todos. Only the workspace owner's todos link to matters, source messages and people, which come from the owner's digest; another member's todo refuses them and never shows their content.
- A todo can be a **goal** with a target date and todos under it (one level), and items can be linked to a goal. A goal shows its progress: done out of everything not dropped, counting a todo handed to a Bot as its item and each item once; with nothing under it yet it shows no percentage.
- A deadline is either a moment or just a day; a day-only deadline keeps its day in every time zone. Todos also hold a reminder time, a snooze time, a priority (0–3), a star, and a repeat rule (daily, weekly, monthly or yearly, every N): completing a repeating todo creates the next one, and undoing the completion takes it back. Reminders are stored but do not notify yet.
- Agents can work with your todos: `steve_todo_list`, `steve_todo_add`, `steve_todo_update` and `steve_todo_complete` (find them with `steve_tools_search`). They only act for the person whose session it is and refuse a session that runs for the workspace; they change only your own todos, at once and undoably, and contact nobody. Dates must be written out (`YYYY-MM-DD` or a time with its offset) and are echoed back.
- The web app no longer reloads its whole state on every digest change; pages that show digest data refresh themselves.

The sign-in page is quieter and livelier: the paragraph about where access tokens come from is gone from under the Sign in button (that guidance stays in `docs/deployment.md`), and Steve's face there is now the live one, whose eyes follow the pointer. It keeps still when the system asks for reduced motion. Bots' faces elsewhere stay static.
