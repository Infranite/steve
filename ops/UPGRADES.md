# Managed GitHub Release upgrades

Steve checks stable releases in `Infranite/steve` (`STEVE_UPDATE_REPOSITORY=owner/repo` overrides it). Settings / Versions shows the Hub and Web versions and the last operation. Instance owners can execute updates. Agents use `steve_upgrade` to check or submit a request; an instance owner must approve the specific version in Settings before it runs. Ordinary workspace ownership does not grant machine-wide upgrade permission.

The managed runtime is the existing `steve-hub` binary with `--supervise`. Your service manager runs `ops/run-managed.sh`; the supervisor owns a child Hub and remains alive when replacing that child. Install an extracted release bundle under `$STEVE_HOME/releases/<version>` and point `$STEVE_HOME/current` to it before starting. Bundles contain `bin/steve-hub`, `web/dist`, and `release.json`. Do not point current at a source checkout or mix independent Hub/Web paths.

Supported implementation targets are Unix macOS and Linux, conditional on a matching release asset. The process tests run locally on macOS; Linux service-manager behavior needs deployment validation. Windows is not supported. Source development and containers managed by an external deployment system expose checks, not an automatic restart button.

For a systemd service, use `Type=simple`, `Restart=on-failure`, `KillMode=control-group`, and `TimeoutStopSec=600`. ExecStart is an absolute path to run-managed.sh. For launchd, use a foreground ProgramArguments entry for that script and KeepAlive. Do not use an asynchronous wrapper that discards the supervisor PID. Stop the whole service before moving an installation or restarting a crashed standalone supervisor. A second supervisor refuses the lock or an occupied Hub port instead of killing an unrelated process. During an upgrade the supervisor finishes the bounded stop/health transaction before processing its pending stop signal; the service manager must allow the timeout above (database backups can take longer; size this for the deployment).

macOS Keychain installations using custom code signatures or `steve-keyhelper` cannot install generic precompiled upgrades: the new Hub would not retain its caller identity. Automatic execution is disabled for them. The updater never replaces the helper or migrates keys. New managed installations can explicitly use the production `STEVE_VAULT_KEYSTORE=dir` backend with `STEVE_VAULT_KEY_DIR` outside STEVE_HOME, on protected storage owned by the Hub user with mode 0700. Keep it mounted across releases. The `file` backend is for isolated development/tests and is refused for the real ~/.steve. Existing Keychain users must plan and authorize a separate key migration; merely changing the variable does not move their keys. Linux can also use its supported Secret Service backend. No keys belong in release assets or the update journal.

Update execution downloads into staging, validates the paired versions, SHA256 and archive paths, then enters durable maintenance and waits for the authenticated drain endpoint to confirm all activity and ACP groups stopped. A failed or timed-out drain is cancelled and leaves the current version running. Only then does it stop the old Hub. Only after it has exited does the supervisor make and integrity-check a SQLite backup. The current symlink switches atomically to the new paired bundle. The candidate runs only schema and read-only existing KEK fingerprint/data-key unwrapping validation and a maintenance health endpoint before the supervisor commits; it cannot run recovery, agents, APIs or background jobs in this gate. Failed candidates are stopped and the old database and bundle restored. Failed databases are preserved as separate evidence. A crash before commit is recoverable from the journal and verified backup.

Commit is the boundary after which business execution may resume. If ordinary boot fails after commit, the updater reports failure and preserves the new database; it must not restore an old snapshot after external effects may have happened. Restarting a committed operation verifies ordinary health before marking it successful. Paused work and pending approvals remain waiting; unknown external delivery outcomes require reconciliation. Durable task resumption is implemented by the task recovery subsystem.

The journal and backups live under `$STEVE_HOME/updates`; operation IDs and errors survive replacing/restoring SQLite. Keep these files until the upgrade has been accepted; this implementation does not automatically delete old versions or backups. An interrupted download is recorded as failed and may be retried with a new idempotency key. A retry of the same key returns its original receipt. The supervisor code itself stays resident through a child update; a later service-manager restart runs the new supervisor from current.

SHA256 protects against corrupted assets; trust comes from the configured GitHub repository and HTTPS. This is not an independent release signature. Release publication must use the manifest format in the release packaging scripts. GitHub rate limits and missing assets are displayed as actionable check/staging errors. No upgrade can be executed before a suitable release has actually been published.

Agent request attribution is deliberately conservative: the current session schema does not record a human owner, so only a workspace with exactly one member who is the instance owner may submit upgrade requests. Shared workspaces can check/status only. Requests expire on the next request after 24 hours; owners can reject them or supersede a pending request by starting their own upgrade. Approval identity/time are recorded. Checks validate the release manifest and the presence of a bundle asset for the current platform before reporting availability. Cache entries are bound to the repository and both installed versions; successful checks and rate-limit errors last ten minutes, while other errors last sixty seconds so transient outages can be retried.

Local validation includes Rust tests with real Python HTTP child stubs (not the Hub), plus `python3 ops/test-upgrade-runtime.py /absolute/debug/steve-hub` with actual Hub processes and temporary STEVE_HOME: paired-version success, incompatible schema rollback, and supervisor crash recovery. This debug fixture has no compiled release identity and executes no Agent task; release builds require embedded version/commit. `cargo test --manifest-path hub-rs/Cargo.toml -p steve-hub --test recovery_ready` separately boots the real Hub with a fake ACP agent and HTTP listener, interrupts a turn, and verifies receipt-aware resumption, partial recovery failure, candidate gating and durable maintenance release. These tests do not execute a real provider or prove exactly-once effects in external systems.

Maintenance authentication uses the 0600 JSON string in `$STEVE_HOME/updates/control-token.json`. Both the supervisor client and Hub control endpoint read that file; it is never injected into child environment variables, so ordinary Agent/flow shell subprocesses do not inherit a control bearer token. Legacy `STEVE_UPGRADE_CONTROL_TOKEN` is explicitly removed when spawning the Hub.

Recovery is bounded: paused tasks and approvals remain waiting, automatic recovery intents expire after 24 hours, and repeated interrupted main-conversation answers require an explicit rerun. Already-delivered queue entries are immutable recovery evidence; editing, withdrawing or forcing them through the queue returns 409. Pause the task to stop subsequent recovery instead.
