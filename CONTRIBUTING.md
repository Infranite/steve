# Contributing to Steve

Thanks for helping. Build and run Steve locally as described in the [README](README.md#quick-start), then use the checks and release rules below.

## How a change gets in

`main` takes changes only through pull requests; nobody pushes to it, and its branch rules require the `CI gate` check of the CI workflow to pass first.

1. Open a GitHub issue for the work, a bug fix included, unless one already covers it.
2. Make a branch from the latest `main`: `git fetch origin && git switch -c <branch> origin/main`.
3. Commit the change with its release-note fragment (below), push the branch and open a pull request into `main` that says `Closes #<issue>`.
4. CI runs on the pull request. When it passed, the pull request is merged (rebase merge). If `main` moved meanwhile and the pull request conflicts, rebase it onto the new `main` and push again.

The full test suite runs in CI, not on your machine: locally, run the checks of what you changed. A pull request runs the Linux jobs (and the Apple apps' build only when it touches them, the web client or the CI workflow); the push to `main` runs both Linux and macOS, and only a head whose own push run passed is released.

## Development checks

```sh
python3 scripts/test-public-boundary.py
python3 scripts/check-public-boundary.py --strict
python3 ops/test-cut-release.py
cargo test --locked --manifest-path hub-rs/Cargo.toml -p steve-install
python3 packaging/homebrew/test-sync.py
python3 ops/cut-release.py lint
cargo test --locked --manifest-path hub-rs/Cargo.toml --workspace
npm run check
npm run test:web
```

CI enforces Rust formatting: run `cargo fmt --all` in `hub-rs/` with the pinned toolchain (`cargo +1.99.1 fmt --all`) before you push.

The workspace suite includes the Node boundary guard (`hub-rs/crates/steve-hub/tests/node_boundary.rs`): production code outside `steve-node` may start processes or harnesses, list directories, or open, write, create or remove files and directories, only at the call sites its table allows, each with a reason; a new one fails until it goes through the Node or is listed. Imports count too, so a braced, renamed or glob `use` of a listed item cannot hide a call. It is a text scan, so it sees where harness handles are made and imported, not every place one is passed to.

The harness parity guard (`hub-rs/crates/steve-hub/tests/harness_parity.rs`, and `web/test/harness-parity.test.mjs` for the web) fails when production code tells harnesses apart by name outside the adapter layer (`steve-acp/src/config.rs`, `steve-acp/src/adapters.rs`). Declare a property in the adapter registry instead. Places that still do are listed in `harness_parity.txt`; the list may only shrink, and `STEVE_PARITY_BLESS=1` rewrites it after removing one.

The full Rust test suite also requires `zsh` at `/bin/zsh` for the existing source-release fixtures (on Debian/Ubuntu, install the `zsh` package). Linux CI and Release jobs install a checksum-pinned hermetic Zsh from GitHub with `scripts/install-ci-zsh.sh`, so they do not depend on Ubuntu package mirrors. The boundary scripts require Python 3.11+. macOS keychain integration tests are explicitly opt-in and create temporary signing resources; ordinary development must not use production credentials. The TypeScript `hub/` workspace is retained for compatibility; the default managed backend is Rust.

To try a change while you work, without CI or a release, run this checkout as a development Hub: `python3 ops/dev.py up` builds the Hub (debug, incremental) and starts it on `127.0.0.1:18440` with the web dev server on `127.0.0.1:18441`; open `http://127.0.0.1:18441/auth/dev` to sign in with one click. Web edits show at once; after a Rust edit, `python3 ops/dev.py restart` rebuilds and restarts the Hub in seconds. Its data is in `~/.steve-dev` (`STEVE_DEV_HOME`), apart from the installed Hub, and stays across restarts. `up --fresh` starts from an empty database where everything runs, sessions included. `up --snapshot` starts from a consistent copy of the installed Hub's database (`--from`, default `~/.steve`), opened as a database copy: nothing resumes, no Node runs and no backup is made, its vault stays locked and new sessions do not run there, so it shows real data without acting on it. Pages on this machine may call the development Hub directly, for example a client switched to `127.0.0.1:18440`: the development web server, the snapshot source's pages (the addresses in its `steve.env`, in snapshot mode), port `5174`, and the origins in `STEVE_DEV_CLIENT_ORIGINS`. `stop`, `status` and `logs` do what they say. Run only the tests of what you changed while you iterate; the full suite runs in CI when the work goes into a pull request.

Development adapter packages live in the development home’s own `adapters` directory; `dev.py` no longer links the installed Hub’s package prefix, and refuses an existing shared symlink. Install the adapters you use into that independent prefix as shown in the README. Claude Code, Codex and Pi each have their own development configuration directory under `harness`; provider sign-in is separate. A snapshot is intentionally read-only with its Node disabled. To switch to runnable development without losing it, stop the development services, move the entire development home to a backup, then run `up --fresh` against a new home; do not enable execution on the copied installation’s queued work.

To try a build by hand with a real harness, use a [second installation](docs/deployment.md#a-second-installation-under-the-same-user): its own `--home`, `--label`, `--listen` port and `--vault-dir`, and, before its first start, [its harnesses' own state directories](docs/deployment.md#its-harnesses-own-state). Without the last, the trial's main conversation keeps its history and memory in your own `~/.claude` or `~/.codex`.

CI (`.github/workflows/ci.yml`) runs on every pull request (Linux jobs, and the Apple job only when the pull request touches the apps, the web client or the workflow) and on every push to `main` (Linux and macOS). Web and release-script checks run independently of Rust. On Linux the web job also runs a few fast browser tests in headless Chromium (`npm run test:web:browser-smoke`; `web/test/browser-smoke.mjs` lists them, and `npx playwright install --only-shell chromium` installs the browser); they answer the API themselves and need no Hub. The other `web/test/*.browser.mjs` tests are run by hand, some against a test Hub built from the checkout. One macOS job runs the Swift package's tests (`scripts/build-apple-client.sh test`) and builds the macOS app and the iOS app for the simulator, unsigned, around the web client of the same commit. Each platform runs the Rust tests in parallel shards, one runner each, with [cargo-nextest](https://nexte.st) 0.9.151 and each test in its own process: `RUST_TEST_SHARDS` at the top of the workflow names how many shards each platform has (fewer on macOS, whose runners are scarce), and nextest's hash partition (`--partition hash:k/N`) decides which tests belong to which shard. Every shard compiles the workspace's tests from its own checkout and runs its share; the first shard also runs the doctests from its build. Nothing is handed between runners but lists and reports: tests run from the checkout and target directory they were compiled in. On Linux, CI builds the tests without debug information (`debug = 0`), which halves their compile time there: a panic message still names its file and line, and a backtrace its functions; macOS keeps line tables, which cost little there. CI disables Rust incremental artifacts and preserves every assertion and the release profile.

Each shard records its build's complete test inventory, its own test list and its JUnit execution report, and `scripts/nextest-summary.py` writes its verdicts to the job summary. The `rust` job of each platform then checks them all (`scripts/nextest-partitions.py`): every shard's build must list the same binaries and tests as the first shard's, and each ordinary test must have been selected by exactly one shard, run exactly once and passed on its first try; opt-in ignored tests remain ignored. Each shard uploads its inventory, list and report with Cargo's build timings (`cargo-timing.html`: how long each crate and test binary took to compile) as a `rust-shard-*` artifact. Automatic retries are disabled (`--retries 0`): a flaky first attempt fails CI and must be investigated. The final `CI gate` requires every job on both platforms to succeed. Every job in both workflows has a time limit (`timeout-minutes`) of two to several times its longest observed run: a job that hangs fails there instead of holding a runner for GitHub's default of six hours.

A push to `main` or a pull request that changed only `docs/releases/` (the release pull request `cut` opens, and the merge commit that brings it into `main`) does not repeat the Rust jobs or the Apple job: nothing they build or test reads that directory. `scripts/skip-rust-jobs.py` waits for this workflow's push run on the commit the change stands on (the commit before the push; the pull request's base, which it must not be behind) and skips them when that run passed, so a passed run always stands on Rust jobs that ran on the same code. They run when that run did not pass, when any other file changed, when the pull request is behind its base, or when GitHub could not say. The other jobs and the gate always run. The workflow also runs on `merge_group`, for GitHub's own merge queue, where the Rust jobs always run.

`cut` accepts only the **entire workflow's** completed successful run, never an individual successful job: the push run on the exact `main` commit it releases from, and the run of its release pull request (see "Only a tested commit is tagged" below).

Official GitHub cache actions restore Rust dependencies under a key made of the platform, the toolchain, the lockfile, every manifest and the workflow file: everything that decides how dependencies are built. Workspace packages are cleaned both after restoring and before saving a cache, so they are always rebuilt from the current checkout. Pull requests only read caches, and one whose key has no cache yet starts from `main`'s newest cache for its platform; only trusted main pushes write them. A push to `main` saves a cache only when its key has none, built from nothing, so there is one cache per dependency set rather than one per push. The release build uses no cache and always compiles from nothing: GitHub's cache scope does not let a tag read another tag's cache, so a cache saved there was never read. The release workflow builds the web assets once alongside native Linux/macOS builds, then packages and verifies each target on its native platform; publication still waits for both complete bundles.

- **No process documents.** Design notes, plans, proposals, specs, reviews, prototypes and runbooks are the maintainers' own thinking and are kept outside the repository. What a user or operator needs goes into the README, `docs/deployment.md` or the release notes; what a reader of the code needs goes into its comments. `python3 scripts/check-public-boundary.py --strict` (run by CI) rejects any other Markdown file, and anything under `docs/` other than `deployment.md`, `releases/` and `assets/`; test fixtures are exempt.

## Changes and releases

A version is chosen when it is released, never ahead on a branch:

- **What the three numbers mean.** Versions are `MAJOR.MINOR.PATCH`.
  - **PATCH** goes up with every ordinary release: features, fixes, interface changes, migrations that run by themselves. Clients and Nodes of the previous release keep working with the new Hub.
  - **MINOR** goes up (and PATCH starts again at 0) for a release that an operator must act on, or should know about before upgrading:
    - the protocol between Hub and Node or Hub and clients changes, so older Nodes or clients must be upgraded first;
    - a feature, setting, API or command-line form is removed or changes meaning;
    - configuration has to be changed by hand;
    - the upgrade cannot be undone by reinstalling the previous release (for example, a migration that older releases cannot read).

    Its release notes start with what to do.
  - **MAJOR** stays 0 until the interfaces and data formats are declared stable. It then becomes 1 once, by hand (`--version 1.0.0`).

  A change that needs a MINOR release says so in the first line of its fragment (`Needs a minor release: <why>`), and whoever cuts the release then passes `--minor`.
- **Release notes are fragments.** A change adds `docs/releases/unreleased/<item>.md` (its item, such as `ST-38.md`, or its branch name): what changes for the user, in a few sentences or bullets, with no version and no title. Do not write `docs/releases/X.Y.Z.md` on a branch; `python3 ops/cut-release.py lint` checks this.
- **Releasing:** after the change is on `main`, run `python3 ops/cut-release.py cut`. It takes `main` as it is on `origin` (its head is the release's base), gives it the next free version (one more than the highest `vX.Y.Z` tag), and commits the fragments joined into `docs/releases/X.Y.Z.md` on that base, removing them; that commit changes nothing else. Because `main` takes nothing but pull requests, the commit goes in as one: `cut` pushes it to `release/vX.Y.Z`, opens a pull request, waits for its CI run (the Rust and Apple jobs are skipped for it, as above), merges it with a merge commit, and then pushes the annotated tag `vX.Y.Z` on the notes commit itself; the tag starts the Release workflow. Other pull requests keep landing on `main` meanwhile, and that does not matter: the merge commit joins the notes to whatever `main` has become, and fragments that arrived after the base stay on `main` for the next release. `cut` closes the release pull request and starts again, a few times at most, only when it does not merge cleanly (a fragment it removes was changed meanwhile), someone else released the version first, or the release branch was taken. The tag is pushed only after the merge, so a merge that fails never leaves a published release that `main` does not contain; a release whose pull request merged but whose tag did not land is finished by the next `cut`, which tags that notes commit as it is. `--dry-run` shows the notes without releasing; `--minor` bumps the minor version. Releasing needs `gh` logged in with the right to open and merge pull requests and to push tags, and branch rules on `main` that allow merge commits and do not require pull requests to be up to date before merging.
- **Only a tested commit is tagged.** `cut` asks GitHub (with `gh`) for the push run on the `main` commit it releases from, which covers both platforms, waits while it runs (`--ci-wait`, 45 minutes by default), and refuses when it failed or there is none; a pull request's run, Linux only, never stands for it. The notes commit then needs its release pull request's run to pass. The tagged commit is exactly that tested base plus the checked release notes, however far `main` has moved since. Investigate test failures before releasing; a rerun is appropriate for a resolved runner or service failure, not a substitute for fixing a flaky test. `--skip-ci` releases without the check, on purpose. If the Release build on the tag fails on a flake, rerun it the same way on the same tag; nothing is published until every target is built.
- **Database migrations** take their number when they are merged: the next free one in `hub-rs/crates/steve-store/migrations`, with a line appended to `LOCK`.
