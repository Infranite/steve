# Contributing to Steve

Thanks for helping. Build and run Steve locally as described in the [README](README.md#quick-start), then use the checks and release rules below.

## How a change gets in

`main` takes changes only through pull requests; nobody pushes to it, and its branch rules require the `CI gate` check of the CI workflow and the `PR description` check to pass first. Editing a pull request's title or description re-runs only `PR description`.

1. Open a GitHub issue for the work, a bug fix included, unless one already covers it.
2. Make a branch from the latest `main`: `git fetch origin && git switch -c <branch> origin/main`.
3. Commit the change using Conventional Commits (`type(scope): imperative summary`, plus an `Upgrade:` trailer when operators must act — see "Changes and releases" below), push the branch and open a pull request into `main` with a matching Conventional Commit title, an optional `## Release note` section in the PR description, and `Closes #<issue>`.
4. CI runs on the pull request, including the PR title format check. When it passed, the pull request is merged (merge commit). If `main` moved meanwhile and the pull request conflicts, rebase it onto the new `main` and push again.

   A pull request opened by an author listed in the repository variable `AUTO_MERGE_AUTHORS` (a JSON array of GitHub logins) merges by itself: the `Auto-merge` workflow (`.github/workflows/auto-merge.yml`) turns on GitHub's auto-merge when the pull request is opened, reopened or marked ready for review, and GitHub merges it once both required checks pass. Pull requests from forks and drafts never qualify. The workflow needs the repository secret `AUTO_MERGE_TOKEN`, a fine-grained token for this repository with Contents and Pull requests read/write. It cannot use the workflow's own `GITHUB_TOKEN`: a merge made with that token does not start the push run on `main` that a release needs.

The full test suite runs in CI, not on your machine: locally, run the checks of what you changed. A pull request into `main` runs the Linux jobs (and the Apple apps' build only when it touches them, the web client or the CI workflow); the push to `main` runs both Linux and macOS, and only a commit whose own full push run passed is released.

On an idle machine, run `python3 ops/bench-backup.py > backup-benchmark.json` to build the release Hub and measure backups and restores of a synthetic 1.5 GB SQLite payload in a disposable installation. The cold pre-upgrade measurement includes repository initialization, which is also reported separately. The other samples cover a pre-upgrade backup in the same repository, a second daily backup with unchanged data, an incremental daily backup after a 10 MB write, a full restore and a database-only restore. Initialization bytes are the size of the new repository files. Backup bytes come from the verified receipts. The timings exclude the build, engine staging, fixture preparation and telemetry readback. A failed run returns a nonzero status and reports any completed samples in the JSON output.

The workspace suite includes the Node boundary guard (`hub-rs/crates/steve-hub/tests/node_boundary.rs`): production code outside the Node crates (`steve-node` and `steve-node-cli`) may start processes or harnesses, list directories, or open, write, create or remove files and directories only at the call sites in `node_boundary.txt`. Each listed rule and file needs a reason in the guard's `RATIONALE` table, and each reason must still have a listed key. A new site fails; a removed site requires shortening the inventory. When the last site for a key disappears, remove its rationale too. Select only the inventory test when rewriting this list, then run the complete Node boundary test binary without BLESS so inventory writes and rationale validation do not race. Diagnostics include source line numbers. Imports count too, so a braced, renamed or glob `use` of a listed item cannot hide a call. This is a text scan of where handles are created or imported, not every place one is passed to.

The harness parity guards (`hub-rs/crates/steve-hub/tests/harness_parity.rs` and `web/test/harness-parity.test.mjs`) fail when production code tells harnesses apart by name outside the adapter layer (`steve-acp/src/config.rs`, `steve-acp/src/adapters.rs`). Declare an adapter property instead. Existing exceptions are counted in the Rust and web parity inventories. The Chinese comparison guards (`zh_compare.rs` and `web/test/guard-zh-compare.test.mjs`) use the same shrinking-inventory rules.

All count inventories use `STEVE_GUARD_BLESS=1` to record a reduction. New keys and increased counts fail even with BLESS; removed keys or reduced counts fail until the list is shortened. BLESS requires an existing inventory and cannot recreate a deleted one. To establish a new inventory explicitly, use `STEVE_GUARD_INIT=1` with its guard: INIT only creates a missing file and refuses to overwrite an existing one. Do not combine INIT and BLESS. Generated snapshots, such as the TypeScript bindings (`cargo test -p steve-types gen`), also use `STEVE_GUARD_BLESS=1` to regenerate their contents; these are equality checks, rather than shrinking count inventories.

The layering guard (`hub-rs/crates/steve-hub/tests/layering.rs`) reads the workspace's production crate dependencies and all `rusqlite` users. `layering.txt` contains reviewed target-architecture edges; changes to this segment require an explicit edit and explanation in review. `layering_debt.txt` contains edges to remove, each with its removal wave and responsible group. Only this debt segment ratchets down; BLESS never rewrites the target segment. Unknown edges fail, and the guard reports target and debt counts separately. Existing domain, integration and adapter dependencies on `steve-i18n` remain shrinking debt; the Hub and installer are edge crates allowed to render text.

To test only what a change can affect, `python3 scripts/affected.py` prints the `-p` arguments for cargo: the crates holding a changed file and every crate that depends on them, dev-dependencies included (`--list` names them). Its base is the merge base with `origin/main`, or `$STEVE_AFFECTED_BASE`, or its first argument. A `Cargo.lock` change touches only the crates that use a package version it added.

The PostgreSQL storage contract job starts an isolated PostgreSQL service and applies the test baseline in `steve-store/src/contract/postgres/`. To run it locally, set `STEVE_TEST_POSTGRES_URL` to an isolated PostgreSQL database and run `cargo test --locked --manifest-path hub-rs/Cargo.toml -p steve-store --lib postgres_contract -- --ignored`. The test owns a temporary schema in that database. Hub installations continue to use the SQLite migration history.

The full Rust test suite also requires `zsh` at `/bin/zsh` for the existing source-release fixtures (on Debian/Ubuntu, install the `zsh` package). Linux CI and Release jobs install a checksum-pinned hermetic Zsh from GitHub with `scripts/install-ci-zsh.sh`, so they do not depend on Ubuntu package mirrors. The boundary scripts require Python 3.11+. macOS keychain integration tests are explicitly opt-in and create temporary signing resources; ordinary development must not use production credentials.

To try a change while you work, without CI or a release, run this checkout as a development Hub: `python3 ops/dev.py up` builds the Hub (debug, incremental) and starts it on `127.0.0.1:18440` with the web dev server on `127.0.0.1:18441`; open `http://127.0.0.1:18441/auth/dev` to sign in with one click. Web edits show at once; after a Rust edit, `python3 ops/dev.py restart` rebuilds and restarts the Hub in seconds. Its data is in `~/.steve-dev` (`STEVE_DEV_HOME`), apart from the installed Hub, and stays across restarts. `up --fresh` starts from an empty database where everything runs, sessions included. `up --snapshot` starts from a consistent copy of the installed Hub's database (`--from`, default `~/.steve`), opened as a database copy: nothing resumes, no Node runs and no backup is made, its vault stays locked and new sessions do not run there, so it shows real data without acting on it. Pages on this machine may call the development Hub directly, for example a client switched to `127.0.0.1:18440`: the development web server, the snapshot source's pages (the addresses in its `steve.env`, in snapshot mode), port `5174`, and the origins in `STEVE_DEV_CLIENT_ORIGINS`. `stop`, `status` and `logs` do what they say. Run only the tests of what you changed while you iterate; the full suite runs in CI when the work goes into a pull request.

Development adapter packages live in the development home's own `adapters` directory; `dev.py` no longer links the installed Hub's package prefix, and refuses an existing shared symlink. Install the adapters you use into that independent prefix as shown in the README. Claude Code, Codex and Pi each have their own development configuration directory under `harness`; provider sign-in is separate. A snapshot is intentionally read-only with its Node disabled. To switch to runnable development without losing it, stop the development services, move the entire development home to a backup, then run `up --fresh` against a new home; do not enable execution on the copied installation's queued work.

To try a build by hand with a real harness, use a [second installation](docs/deployment.md#a-second-installation-under-the-same-user): its own `--home`, `--label`, `--listen` port and `--vault-dir`, and, before its first start, [its harnesses' own state directories](docs/deployment.md#its-harnesses-own-state). Without the last, the trial's main conversation keeps its history and memory in your own `~/.claude` or `~/.codex`.

For sustained main-chat performance, run `BENCH_PORT=<port> npm run bench:web:chat -- --gate` against a disposable loopback release Hub serving `npm run build:web` output, with dev login, an empty home or a private SQLite copy, `STEVE_NO_RESUME=1` and `STEVE_FORBID_REAL_HOSTS=1`. Never point it at an installed Hub. Install Playwright Chromium first (`npx playwright install --only-shell chromium`). The scenario replaces the browser's live stream with a loopback SSE fixture, reads history and the shell from the test Hub, waits for a one-minute load average of at most 3, then streams for 60 seconds while opening process cards, scrolling both ways and editing an unsent draft. It emits aggregate JSON only. On a host that does not allow Chromium's Mach rendezvous, use `BENCH_SINGLE_PROCESS=1` on both runs. For separate React commit and component counts, serve the output of `npm -w web exec -- vite build --minify false --outDir <dir>` and run with `--profile` instead of `--gate`; do not compare those instrumented frame timings with the normal build.

Use `BENCH_MAX_DROPPED=<baseline count>` with `--gate` to check for a regression in estimated dropped frames. For diagnosis, set `BENCH_TRACE=<new file prefix>` on a separate run without `--gate` or `--profile`. The Chromium timeline and frame timestamps are saved locally as private JSON files; align the timestamps with the `chat-bench-start` trace marker. These files can contain local request URLs and are not for publication.

CI (`.github/workflows/ci.yml`) runs on pull requests targeting `main` (Linux jobs, including `release-check`, and the Apple job only when the pull request touches the apps, the web client or the workflow) and pushes to `main` (Linux and macOS). Pull requests into integration branches do not trigger it. Main pushes share one concurrency group without cancelling its running workflow: GitHub keeps one running and at most one pending run, replacing the pending run when a newer push arrives. Pull requests keep cancelling older runs of the same pull request; merge queue runs keep their own SHA groups, separate from main pushes. Web and release-script checks run independently of Rust. The web job runs on Linux only: its type checks, unit tests and build are the same TypeScript on every platform, and the Apple job builds the web client again on macOS. The `release-check` job runs on Linux after `web`, reusing `web/dist` and its own trusted third-party dependency cache in `dev` profile without debug info: it builds `steve`, `steve-hub`, `steve-node`, and `steve-keyhelper` with compile-time release identity (`STEVE_RELEASE_VERSION=0.0.0`, `STEVE_RELEASE_COMMIT=$GITHUB_SHA`, without `[dev-dependencies]`), packages both the runtime and installer bundles with `scripts/package-release.py package`, and verifies the manifests, archive layout (`packaging/homebrew/tap/sync.py`), unpacked binaries, and booted Hub (`scripts/package-release.py verify` + `ops/test-release-identity.py`). The release and boundary script checks (`scripts/ci-script-checks.sh`, one list for both platforms) run in the `scripts` job on Linux and, on macOS, in the first macOS Rust shard before it compiles, which saves a scarce macOS runner. On pull requests, the `scripts` job also enforces Conventional Commit PR titles and valid release trailers (`ops/cut-release.py lint --github-event`). The web job also runs headless Chromium browser tests (`npx playwright install --only-shell chromium` installs the browser); every `web/test/*.browser.mjs` file answers the API itself without a real Hub and belongs to one of two CI tiers enforced by `web/test/browser-inventory.test.mjs` (no manual-only tier): fast tests (<= `CI_SMOKE_THRESHOLD_S` = 30 s on CI) run in the `web` job via `npm run test:web:browser-smoke` (`SMOKE` in `web/test/browser-smoke.mjs`), and slow tests (> 30 s on CI) run in the sharded `browser-extended` job via `npm run test:web:browser-extended -- --shard=k/N` (`EXTENDED` in `web/test/browser-smoke.mjs`) whenever web files change. One macOS job runs the Swift package's tests (`scripts/build-apple-client.sh test`) and builds the macOS app and the iOS app for the simulator, unsigned, around the web client of the same commit. Each platform runs the Rust tests in parallel shards, one runner each, with [cargo-nextest](https://nexte.st) 0.9.151 and each test in its own process: `RUST_TEST_SHARDS` at the top of the workflow names how many shards each platform has (fewer on macOS, whose runners are scarce), and nextest's hash partition (`--partition hash:k/N`) decides which tests belong to which shard. Every shard compiles the workspace's tests from its own checkout and runs its share; the first shard also runs the doctests from its build. Nothing is handed between runners but lists and reports: tests run from the checkout and target directory they were compiled in. On Linux, CI builds the tests without debug information (`debug = 0`), which halves their compile time there: a panic message still names its file and line, and a backtrace its functions; macOS keeps line tables, which cost little there. CI disables Rust incremental artifacts and preserves every assertion and the release profile.

Each shard records its build's complete test inventory, its own test list and its JUnit execution report, and `scripts/nextest-summary.py` writes its verdicts to the job summary. The `rust` job of each platform then checks them all (`scripts/nextest-partitions.py`): every shard's build must list the same binaries and tests as the first shard's, and each ordinary test must have been selected by exactly one shard, run exactly once and passed on its first try; opt-in ignored tests remain ignored. Each shard uploads its inventory, list and report with Cargo's build timings (`cargo-timing.html`: how long each crate and test binary took to compile) as a `rust-shard-*` artifact. Automatic retries are disabled (`--retries 0`): a flaky first attempt fails CI and must be investigated. The final `CI gate` requires every job in its own run to succeed (both platforms outside pull requests). A cancelled run fails its own gate (a skipped required check would count as passed); that failure stays on its commit, and `cut` never takes a cancelled run as tested. Every job in both workflows has a time limit (`timeout-minutes`) of two to several times its longest observed run: a job that hangs fails there instead of holding a runner for GitHub's default of six hours. GitHub's hosted macOS arm64 runners are sometimes all taken; GitHub then cancels a waiting job itself after about 15 minutes, with no step run ("The job was not acquired by Runner of type hosted even after multiple attempts"). When a push run on `main` fails, the `CI rerun` workflow (`.github/workflows/ci-rerun.yml`, `scripts/rerun-unacquired.py`) reruns its failed jobs, but only when every failure is such an unacquired job, or the `CI gate` and a platform's `rust` job that only report on it, at most three times per run, and only while no newer push to `main` has a CI run: a rerun goes back into the `main` concurrency group, where it would cancel that newer run's pending place. A job that ran a step and failed is never rerun. `cut` takes a run's latest attempt.

A push to `main` or a pull request that changed only `docs/releases/` (the release pull request `cut` opens, and the merge commit that brings it into `main`) does not repeat the Rust jobs, the `release-check` job, or the Apple job: nothing they build or test reads that directory. `scripts/skip-rust-jobs.py` waits for this workflow's push run on the commit the change stands on (the commit before the push; the pull request's base, which it must not be behind) and skips them when that run passed, so a passed run always stands on Rust jobs that ran on the same code. They run when that run did not pass, when any other file changed, when the pull request is behind its base, or when GitHub could not say. The other jobs and the gate always run. The workflow also runs on `merge_group`, for GitHub's own merge queue, where the Rust jobs always run.

`cut` accepts only the **entire workflow's** completed successful run, never an individual successful job: the push run on the exact `main` commit it releases from, and the run of its release pull request (see "Only a tested commit is tagged" below).

Official GitHub cache actions restore Rust dependencies under a key made of the platform, the toolchain, the lockfile, every manifest and the workflow file: everything that decides how dependencies are built. Workspace packages are cleaned both after restoring and before saving a cache, so they are always rebuilt from the current checkout. Pull requests only read caches, and one whose key has no cache yet starts from `main`'s newest cache for its platform; only trusted main pushes write them. A push to `main` saves a cache only when its key has none, built from nothing, so there is one cache per dependency set rather than one per push. The release build uses no cache and always compiles from nothing: GitHub's cache scope does not let a tag read another tag's cache, so a cache saved there was never read. The release workflow builds the web assets once alongside native Linux/macOS builds, then packages and verifies each target on its native platform; publication still waits for both complete bundles.

- **No process documents.** Design notes, plans, proposals, specs, reviews, prototypes and runbooks are the maintainers' own thinking and are kept outside the repository. What a user or operator needs goes into the README, `docs/architecture.md`, `docs/concepts.md`, `docs/deployment.md` or the release notes; what a reader of the code needs goes into its comments. `python3 scripts/check-public-boundary.py` (run by CI) rejects any other Markdown file, and anything under `docs/` other than `architecture.md`, `concepts.md`, `deployment.md`, `releases/<X.Y.Z>.md` and `assets/`; only explicitly allowlisted test fixture directories are exempt from the process-document path rule, and they are still scanned for private identifiers and proposal headers. Maintainers can provide private personal-identifier rules outside the repository via `--rules`, `STEVE_PUBLIC_BOUNDARY_RULES`, or `STEVE_PUBLIC_BOUNDARY_PATTERNS`.

## Changes and releases

Release artifacts are built without Apple Developer ID signing certificates; on macOS, the installer creates and reuses a machine-local self-signed signing identity inside each Hub or Node home during installation and upgrades.

Versions and release notes are generated automatically from commits at release time, never chosen ahead on a branch:

- **What the three numbers mean (`MAJOR.MINOR.PATCH`).**
  - **MAJOR** marks the stability generation of Steve's public contracts (Hub HTTP API, Hub–Node protocol, plugin SDK, and data formats). It stays `0` until stability is declared, and becomes `1.0.0` once the contracts are frozen. After `1.0`, MAJOR increments only on incompatible public-contract changes that require manual operator migration (and resets MINOR and PATCH to `0`).
  - **MINOR** increments (and resets PATCH to `0`) when a release adds user-visible capabilities, or requires operator action or awareness when upgrading:
    - Hub, Nodes, or clients must upgrade together;
    - a protocol between Hub and Node or Hub and clients changes;
    - a data migration cannot be undone by reinstalling the previous release;
    - manual configuration is required;
    - a feature, setting, API, or CLI behavior is removed or changes meaning.

    Before `1.0`, breaking changes also increment MINOR.
  - **PATCH** increments when a release contains only fixes, performance improvements, documentation, or internal refactoring. Operators can install it in place and roll back by reinstalling the previous release.
- **Commit and pull request format (Conventional Commits).**
  - Every commit subject and pull request title uses `type(scope): imperative summary` (or `type: imperative summary`), where `type` is one of `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `revert`.
  - Mark incompatible public-contract changes with `!` after the type/scope (for example `feat(api)!: ...`) or a `BREAKING CHANGE: <why>` trailer.
  - When operators must act before or after upgrading, add a trailer `Upgrade: <what to do>` (may span multiple lines) in the pull request description (or in the commit message for direct commits without a pull request). For pull requests, `Upgrade:` and `BREAKING CHANGE:` notices are read **only** from the pull request description — never falling back to commit trailers, so superseded draft commit wording cannot leak into release notes; identical notices are deduplicated across the section.
  - Pull requests merge into `main` with merge commits; when multiple pull requests land together through an integration pull request, `ops/cut-release.py` lists merged pull requests from GitHub GraphQL over the release window and filters by `mergeCommit` in the release range, emitting each carried sub-PR individually and rendering a `chore` carrier pull request as a single line under `Other changes` listing its carried sub-PR numbers. Add an optional `## Release note` section to the PR description for user-facing context; when omitted, the PR title is used. `## Release note` runs until the next Markdown heading, so place sections in this order (keeping test summaries and any trailing signature out of `## Release note`):

    ```markdown
    ## Release note

    Concise user-facing summary of what changed.

    Upgrade: optional operator action before or after upgrading.

    ## Checks

    Checks and tests run for this pull request.

    <!-- Optional attribution / signature line goes after ## Checks -->
    ```

    Direct commits without a merged PR use their commit subject.
  - **Node wire protocol (`PROTOCOL`) bumps.** `PROTOCOL` in `hub-rs/crates/steve-node-api/src/lib.rs` is compared for exact equality: any mismatch forces remote Nodes into upgrade-only mode until the Hub and Nodes upgrade together. Increment `PROTOCOL` (by `+1` only) strictly for breaking wire-format or semantic changes (`remove-or-rename`, `type-narrowing`, `required-field`, `semantic-break`, or `transport-frame`); never increment it for additive `#[serde(default)]` fields on non-strict structs. A pull request that increments `PROTOCOL` must include both a `Protocol-Bump: <category> — <reason>` trailer (with `<category>` in that allowlist and at least 15 non-whitespace characters naming the affected wire types and why `#[serde(default)]` or capability negotiation cannot cover it) and an `Upgrade:` trailer in the PR description, and update the baseline JSON fixtures under `hub-rs/crates/steve-node-api/tests/fixtures/ordinary_compat/`. Existing baseline fixtures under `tests/fixtures/ordinary_compat/` may not be modified, renamed, or deleted unless `PROTOCOL` increments (adding new fixtures without a bump is allowed).
  - The `PR description` check rejects pull requests whose title does not follow this format, whose description lacks an issue link (`Closes #N`, `Fixes #N`, or `Resolves #N` outside fenced code blocks; `chore(release):` PRs are exempt), whose release trailers are empty, whose commits contain an `Upgrade:` trailer while the PR description has none (except `chore(integration)` carrier PRs), whose `## Release note` section contains a `Checks:` paragraph or a signature/attribution line (move them under a separate heading such as `## Checks`), that change `PROTOCOL` without a `+1` step, valid `Protocol-Bump:` trailer, and `Upgrade:` trailer, that modify or delete existing `tests/fixtures/ordinary_compat/` fixtures without incrementing `PROTOCOL`, or that add, modify, or delete files under `docs/releases/` (except a `chore(release): vX.Y.Z` release PR adding `docs/releases/X.Y.Z.md` alone), via `ops/cut-release.py lint --github-event` (re-run on PR `edited` events as well). Locally, `python3 ops/cut-release.py lint` enforces the same branch commit, `docs/releases/`, single-step `PROTOCOL`, and baseline-fixture lock rules (use `--range A..B` to check any commit range, or `--pr-title`/`--pr-body` with `--base`/`--range` to check a PR description against its branch commits and diff).
- **Automatic version calculation and release notes.**
  - `ops/cut-release.py` lists merged pull requests from GitHub via GraphQL over the release range's time window, keeps those whose `mergeCommit.oid` lies in the release range since the highest `vX.Y.Z` tag (covering both direct merges and sub-PRs sharing an integration PR's merge commit), uses live PR titles and descriptions from GitHub (so editing a merged PR's title or description on GitHub takes effect immediately), and computes the next version automatically across all resolved PRs and direct commits:
    - `!` or `BREAKING CHANGE:` → **MAJOR** after `1.0`, **MINOR** before `1.0`;
    - `feat` or any `Upgrade:` trailer → **MINOR**;
    - anything else → **PATCH**.
  - If any commit or PR title in the range does not match Conventional Commits, `next` and `cut` refuse and list every offending PR/commit so its PR title and description can be updated on GitHub before re-running.
  - Neither humans nor agents pick versions on a branch. `--version X.Y.Z --reason "<why>"` is reserved for maintainer overrides (such as cutting `1.0.0` when freezing contracts or correcting a misclassified history); the reason is recorded at the top of the generated release notes.
  - `python3 ops/cut-release.py next` prints the computed next version and lists the exact commits that triggered a MINOR or MAJOR bump (supports `--range FROM..TO` and `--offline`).
  - `python3 ops/cut-release.py cut --dry-run` prints the complete generated release notes without selecting a tested base, asking CI, or pushing anything (supports `--range FROM..TO` and `--offline`).
  - Generated notes follow a fixed structure so every change in the release range is accounted for: **Before upgrading** (all `Upgrade:` and breaking notices, pinned at the top) → **Features** → **Fixes** → **Performance** → **Other changes** (`refactor`, `docs`, `test`, `build`, `ci`, `chore`, `revert`, listed without omission), each linked to its PR or commit.
- **Releasing:** after changes are on `main`, run `python3 ops/cut-release.py cut`. It selects the newest tested first-parent commit on `origin/main` as `base`, computes the version and release notes from the commits between the previous tag and `base`, and commits `docs/releases/X.Y.Z.md` on `base` (`chore(release): vX.Y.Z`, changing nothing else). Because `main` takes nothing but pull requests, that commit goes in as one: `cut` pushes it to `release/vX.Y.Z`, opens a pull request titled `chore(release): vX.Y.Z`, waits for its CI run (release-notes-only PRs skip Rust, PostgreSQL, and Apple as above; a pull request behind `main` runs them again), merges it with a merge commit (`--match-head-commit`), and then pushes the annotated tag `vX.Y.Z` on the notes commit itself; the tag starts the Release workflow. Other pull requests keep landing on `main` meanwhile, and that does not matter: the merge commit joins the notes commit to whatever `main` has become, and commits that arrived after `base` wait for the next release. `cut` closes the release pull request and starts again, a few times at most, only on a real race (a merge conflict, someone else releasing the version first, or a taken release branch). The tag is pushed only after the merge, so a merge that fails never leaves a published release that `main` does not contain; a release whose pull request merged but whose tag did not land is finished by the next `cut`, which finds the untagged `chore(release): vX.Y.Z` commit and tags it as it is. Releasing needs `gh` logged in with the right to open and merge pull requests and to push tags, and branch rules on `main` that allow merge commits and do not require pull requests to be up to date before merging.
- **Only a tested commit is tagged.** `cut` walks `main`'s first-parent history since the last release and picks the newest commit containing new changes whose own latest full push run completed successfully on both platforms. Newer running, cancelled or failed commits wait for the next release (and do not affect the version bump of the older tested `base`). Cancelled runs never count as successful tests, and a pull request's run, Linux only, never stands for a push run. If no eligible commit passed, `cut` checks the current head, waits while it runs (`--ci-wait`, 45 minutes by default), and refuses when it failed or there is no push run. The notes commit then needs its release pull request's run to pass. The tagged commit is exactly that tested base plus the generated release notes, however far `main` has moved since. Investigate test failures before releasing; a rerun is appropriate for a resolved runner or service failure, not a substitute for fixing a flaky test. `--skip-ci` releases without the check, on purpose. If the Release build on the tag fails on a flake, rerun it the same way on the same tag; nothing is published until every target is built.
- **Database migrations** take their number when they are merged: the next free one in `hub-rs/crates/steve-store/migrations`, with a line appended to `LOCK`.
