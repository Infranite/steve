# Contributing to Steve

Thanks for helping. Build and run Steve locally as described in the [README](README.md#quick-start), then use the checks and release rules below.

## How a change gets in

`main` takes changes only through pull requests; nobody pushes to it, and its branch rules require the `CI gate` check of the CI workflow to pass first.

1. Open a GitHub issue for the work, a bug fix included, unless one already covers it.
2. Make a branch from the latest `main`: `git fetch origin && git switch -c <branch> origin/main`.
3. Commit the change with its release-note fragment (below), push the branch and open a pull request into `main` that says `Closes #<issue>`.
4. CI runs on the pull request. When it passed, the pull request is merged (rebase merge). If `main` moved meanwhile and the pull request conflicts, rebase it onto the new `main` and push again.

The full test suite runs in CI, not on your machine: locally, run the checks of what you changed. A pull request into `main` runs the Linux jobs, a macOS structure check when it touches `hub-rs/**`, `scripts/structure_guard.py` or `.github/workflows/ci.yml`, and the Apple apps' build only when it touches them, the web client or the CI workflow; the push to `main` runs both Linux and macOS, and only a commit whose own full push run passed is released.

CI enforces Rust formatting: run `cargo fmt --all` in `hub-rs/` with the pinned toolchain (`cargo +1.99.1 fmt --all`) before you push.

The workspace suite includes the Node boundary guard (`hub-rs/crates/steve-hub/tests/node_boundary.rs`): production code outside the Node crates (`steve-node` and `steve-node-cli`) may start processes or harnesses, list directories, or open, write, create or remove files and directories only at the call sites in `node_boundary.txt`. Each listed rule and file needs a reason in the guard's `RATIONALE` table, and each reason must still have a listed key. A new site fails; a removed site requires shortening the inventory. When the last site for a key disappears, remove its rationale too. Select only the inventory test when rewriting this list, then run the complete Node boundary test binary without BLESS so inventory writes and rationale validation do not race. Diagnostics include source line numbers. Imports count too, so a braced, renamed or glob `use` of a listed item cannot hide a call. This is a text scan of where handles are created or imported, not every place one is passed to.

The harness parity guards (`hub-rs/crates/steve-hub/tests/harness_parity.rs` and `web/test/harness-parity.test.mjs`) fail when production code tells harnesses apart by name outside the adapter layer (`steve-acp/src/config.rs`, `steve-acp/src/adapters.rs`). Declare an adapter property instead. Existing exceptions are counted in the Rust and web parity inventories. The Chinese comparison guards (`zh_compare.rs` and `web/test/guard-zh-compare.test.mjs`), runtime policy guard and test sleep guard use the same shrinking-inventory rules.

All count inventories use `STEVE_GUARD_BLESS=1` to record a reduction. New keys and increased counts fail even with BLESS; removed keys or reduced counts fail until the list is shortened. BLESS requires an existing inventory and cannot recreate a deleted one. To establish a new inventory explicitly, use `STEVE_GUARD_INIT=1` with its guard: INIT only creates a missing file and refuses to overwrite an existing one. Do not combine INIT and BLESS. Generated snapshots, such as the TypeScript bindings (`cargo test -p steve-types gen`) and SQLite schema baselines, also use `STEVE_GUARD_BLESS=1` to regenerate their contents; these are equality checks, rather than shrinking count inventories.

The layering guard (`hub-rs/crates/steve-hub/tests/layering.rs`) reads the workspace's production crate dependencies and all `rusqlite` users. `layering.txt` contains reviewed target-architecture edges; changes to this segment require an explicit edit and explanation in review. `layering_debt.txt` contains edges to remove, each with its removal wave and responsible group. Only this debt segment ratchets down; BLESS never rewrites the target segment. Unknown edges fail, and the guard reports target and debt counts separately. Existing domain, integration and adapter dependencies on `steve-i18n` remain shrinking debt; the Hub and installer are edge crates allowed to render text.

`python3 scripts/structure_guard.py` checks all workspace targets, then uses production lib/bin Clippy diagnostics to guard function length (100 lines) and cognitive complexity (25). `hub-rs/structure.txt` records a descending numeric multiset for each `(crate, file, lint)` key. A new key, more values, or a higher paired value fails, including with BLESS. A reduction requires `STEVE_GUARD_BLESS=1` (or `--bless`); a missing inventory requires explicit INIT. Function names and line positions are not identities, so moving a function within a file does not create a new entry. `python3 scripts/test_structure_guard.py` tests parsing and comparison without compiling Rust. The inventory covers the current host and selected features; calibrate it before enforcing the same list on another platform or feature set.

CI tests the structure parser and inventory comparator in the Python job. A separate `structure` job on `macos-15` installs Clippy and runs only `python3 scripts/structure_guard.py`. For pull requests, `changes` includes this job when any current or previous changed path is under `hub-rs/` or equals `scripts/structure_guard.py` or `.github/workflows/ci.yml`; it skips the job otherwise and runs it conservatively if the file query fails. Push and merge queue runs always include it unless cancelled, independently of Rust test skipping. The CI gate requires its success, allowing it to be skipped only for a pull request that `changes` confirmed changes none of these structure inputs. This inventory has one macOS truth, matching the local gate; Linux-only functions are outside its coverage. Rust test shards do not repeat this Clippy pass.

`python3 scripts/check-inventory-growth.py --base "$(git merge-base origin/main HEAD)"` compares committed inventory snapshots; it does not read a rewritten working copy. In CI, a pull request uses its target branch SHA and verifies that the tested merge commit has exactly the payload base and head as its two parents, in base/head order. If this assertion fails because the payload base SHA no longer matches the tested merge's first parent, push another commit (an empty commit is sufficient) to generate a fresh event; rerunning the old workflow keeps its old payload and cannot fix it. A fast-forward push compares `before..HEAD`, covering every rebased commit in that push. Only an all-zero before (new branch) or a confirmed non-ancestor before (force push) falls back to `HEAD^`; the log states the reason. Missing before history fails unless the payload explicitly confirms a force push; that fallback is also logged. A merge queue run uses its base SHA. Count inventories under `steve-hub/tests/` (including `due_wake_sites.txt`), SQLite inventory sidecars and schema debt/trigger lists, `steve-store-sqlite/tests/digest_write_sites.txt`, `steve-flow/tests/run_write_ownership.txt`, the two web inventories, and `hub-rs/structure.txt` may only shrink. `layering.txt` is the reviewed target segment and is excluded. Structure values use the same descending-multiset comparison as the structure guard. Schema debt identities are `(kind, id)`, and trigger identities are names; editing their descriptive metadata does not add an identity. Layering debt includes the removal wave and owner in its key, so reassignment or postponement requires an explicit review too.

CI uses the same budget comparison as the local structure guard: for each key, the number of values cannot increase, and the descending values cannot exceed their baseline bounds. Normal reductions need no approval. The comparison does not infer function identities from anonymous numbers or from a global count.

A reviewed budget increase needs a Git trailer naming the path, key and **complete head result**:

```text
Inventory-Growth: hub-rs/structure.txt example	crates/example/src/x.rs	too_many_lines = 120,110: why this result is required
```

Copy the key and result printed by the comparator, preserving the literal TAB separators between key fields (as in the inventory row and the example above); replacing them with spaces does not authorize growth. Use `printf` to generate actual TAB characters (for example, `printf '%b\n' 'Inventory-Growth: hub-rs/structure.txt example\tcrates/example/src/x.rs\ttoo_many_lines = 120,110: reason'`), or put a commit message containing actual TAB characters in a file and use `git commit -F <file>`. Copying from web logs may turn TABs into spaces; such a marker will be rejected, never granted broader authorization. Spaces inside a key field remain part of that field. Structure results are descending comma-separated lists; count inventories use a single count. The authorization applies only to that key with exactly that result. If the result changes again while still above the baseline budget, it needs a new authorization. A path-only marker cannot approve growth, nor can a marker for another key or an older result.

`digest_write_sites.txt` compares each `(kind, path)` count. `run_write_ownership.txt` compares the `total` and `bare` counts as separate named keys per path: `bare=0` is a real budget, and lowering `total` cannot offset an increase in `bare`. A two-column legacy file has an unknown `bare` baseline. Changing an existing file between two and three columns needs an explicit layout review as well as exact-result reasons for any newly introduced or growing keys; it cannot use a first-import anchor. For example (preserve the literal TAB in the count key):

```text
Inventory-Growth: hub-rs/crates/steve-flow/tests/run_write_ownership.txt: format 2->3: explain the reviewed column semantics
Inventory-Growth: hub-rs/crates/steve-flow/tests/run_write_ownership.txt src/example.rs	bare = 0: explain this new column's exact budget
```

A format review does not authorize removing the file later. `due_wake_sites.txt` uses one `(file, count)` pair per row through the same Hub-test inventory discovery.

For the first import of a nonempty inventory, review a particular Git blob and anchor that version:

```text
Inventory-Growth: hub-rs/structure.txt: import 0b5a8a36ebd3aeacc6e30c96a93437b7c40ef8ea: reviewed initial macOS budget
```

Use the full 40-character blob id. The comparator verifies that this blob appeared at this exact path within the candidate's comparison history, then uses its contents as that new path's baseline. Later increases still need the key/result form; reductions do not. Imports do not reset a path already present in the target baseline, and conflicting import anchors fail. This also applies to the first reform branch candidate into main: the import anchor approves its snapshot, not every later change to the file.

`python3 scripts/inventory-import-markers.py --base origin/main --head HEAD` prepares first-import trailers from committed Git snapshots. Review the anchored blobs before adding its output to a candidate commit message. It follows this comparator's inventory discovery, including the exclusion of target `layering.txt`; it does not add new guard families to the comparator.

RG4's import syntax shares the `Inventory-Growth:` trailer key shown above, but this helper emits only the `: import <40-character blob>:` form. It never generates key/result growth or removal authorization. If an existing inventory grows or is removed, the helper prints no trailers at all, explains the required human review on stderr, and exits 1. Invalid input exits 2; an unchanged or shrinking baseline, or an empty new list, needs no import trailer. Uncommitted and staged edits do not affect its output.

Keep empty inventory files. Removing a file or moving it outside discovery requires naming its original path with a removal reason (`Inventory-Growth: <path>: <removal reason>`); this form cannot authorize budget growth. Separate trailers from the commit body with a blank line. Markers are considered only in the comparison range, and the log prints each key's required result and every applied marker. Marker presence records intent; reviewers must assess the change. Deleting and INIT-recreating a list, or editing it by hand, cannot bypass the Git snapshot comparison. Malformed data fails even with a marker. Global totals are reference information because increases and reductions can cancel.

To test only what a change can affect, `python3 scripts/affected.py` prints the `-p` arguments for cargo: the crates holding a changed file and every crate that depends on them, dev-dependencies included (`--list` names them). Its base is the merge base with `origin/main`, or `$STEVE_AFFECTED_BASE`, or its first argument. A `Cargo.lock` change touches only the crates that use a package version it added.

The full Rust test suite also requires `zsh` at `/bin/zsh` for the existing source-release fixtures (on Debian/Ubuntu, install the `zsh` package). Linux CI and Release jobs install a checksum-pinned hermetic Zsh from GitHub with `scripts/install-ci-zsh.sh`, so they do not depend on Ubuntu package mirrors. The boundary scripts require Python 3.11+. macOS keychain integration tests are explicitly opt-in and create temporary signing resources; ordinary development must not use production credentials. The TypeScript `hub/` workspace is retained for compatibility; the default managed backend is Rust.

To try a change while you work, without CI or a release, run this checkout as a development Hub: `python3 ops/dev.py up` builds the Hub (debug, incremental) and starts it on `127.0.0.1:18440` with the web dev server on `127.0.0.1:18441`; open `http://127.0.0.1:18441/auth/dev` to sign in with one click. Web edits show at once; after a Rust edit, `python3 ops/dev.py restart` rebuilds and restarts the Hub in seconds. Its data is in `~/.steve-dev` (`STEVE_DEV_HOME`), apart from the installed Hub, and stays across restarts. `up --fresh` starts from an empty database where everything runs, sessions included. `up --snapshot` starts from a consistent copy of the installed Hub's database (`--from`, default `~/.steve`), opened as a database copy: nothing resumes, no Node runs and no backup is made, its vault stays locked and new sessions do not run there, so it shows real data without acting on it. Pages on this machine may call the development Hub directly, for example a client switched to `127.0.0.1:18440`: the development web server, the snapshot source's pages (the addresses in its `steve.env`, in snapshot mode), port `5174`, and the origins in `STEVE_DEV_CLIENT_ORIGINS`. `stop`, `status` and `logs` do what they say. Run only the tests of what you changed while you iterate; the full suite runs in CI when the work goes into a pull request.

Development adapter packages live in the development home's own `adapters` directory; `dev.py` no longer links the installed Hub's package prefix, and refuses an existing shared symlink. Install the adapters you use into that independent prefix as shown in the README. Claude Code, Codex and Pi each have their own development configuration directory under `harness`; provider sign-in is separate. A snapshot is intentionally read-only with its Node disabled. To switch to runnable development without losing it, stop the development services, move the entire development home to a backup, then run `up --fresh` against a new home; do not enable execution on the copied installation's queued work.

To try a build by hand with a real harness, use a [second installation](docs/deployment.md#a-second-installation-under-the-same-user): its own `--home`, `--label`, `--listen` port and `--vault-dir`, and, before its first start, [its harnesses' own state directories](docs/deployment.md#its-harnesses-own-state). Without the last, the trial's main conversation keeps its history and memory in your own `~/.claude` or `~/.codex`.

CI (`.github/workflows/ci.yml`) runs on pull requests targeting `main` (Linux jobs, the macOS `structure` job when the pull request touches `hub-rs/**`, `scripts/structure_guard.py` or `.github/workflows/ci.yml`, and the Apple job only when it touches the apps, the web client or the workflow) and pushes to `main` (Linux and macOS). Pull requests into integration branches do not trigger it. Main pushes share one concurrency group without cancelling its running workflow: GitHub keeps one running and at most one pending run, replacing the pending run when a newer push arrives. Pull requests keep cancelling older runs of the same pull request; merge queue runs keep their own SHA groups, separate from main pushes. Web and release-script checks run independently of Rust. The web job runs on Linux only: its type checks, unit tests and build are the same TypeScript on every platform, and the Apple job builds the web client again on macOS. The release and boundary script checks (`scripts/ci-script-checks.sh`, one list for both platforms) run in the `scripts` job on Linux and, on macOS, in the first macOS Rust shard before it compiles, which saves a scarce macOS runner. The web job also runs a few fast browser tests in headless Chromium (`npm run test:web:browser-smoke`; `web/test/browser-smoke.mjs` lists them, and `npx playwright install --only-shell chromium` installs the browser); they answer the API themselves and need no Hub. The other `web/test/*.browser.mjs` tests are run by hand, some against a test Hub built from the checkout. One macOS job runs the Swift package's tests (`scripts/build-apple-client.sh test`) and builds the macOS app and the iOS app for the simulator, unsigned, around the web client of the same commit. Each platform runs the Rust tests in parallel shards, one runner each, with [cargo-nextest](https://nexte.st) 0.9.151 and each test in its own process: `RUST_TEST_SHARDS` at the top of the workflow names how many shards each platform has (fewer on macOS, whose runners are scarce), and nextest's hash partition (`--partition hash:k/N`) decides which tests belong to which shard. Every shard compiles the workspace's tests from its own checkout and runs its share; the first shard also runs the doctests from its build. Nothing is handed between runners but lists and reports: tests run from the checkout and target directory they were compiled in. On Linux, CI builds the tests without debug information (`debug = 0`), which halves their compile time there: a panic message still names its file and line, and a backtrace its functions; macOS keeps line tables, which cost little there. CI disables Rust incremental artifacts and preserves every assertion and the release profile.

Each shard records its build's complete test inventory, its own test list and its JUnit execution report, and `scripts/nextest-summary.py` writes its verdicts to the job summary. The `rust` job of each platform then checks them all (`scripts/nextest-partitions.py`): every shard's build must list the same binaries and tests as the first shard's, and each ordinary test must have been selected by exactly one shard, run exactly once and passed on its first try; opt-in ignored tests remain ignored. Each shard uploads its inventory, list and report with Cargo's build timings (`cargo-timing.html`: how long each crate and test binary took to compile) as a `rust-shard-*` artifact. Automatic retries are disabled (`--retries 0`): a flaky first attempt fails CI and must be investigated. The final `CI gate` requires every job in its own run to succeed (both platforms outside pull requests). A cancelled run fails its own gate (a skipped required check would count as passed); that failure stays on its commit, and `cut` never takes a cancelled run as tested. Every job in both workflows has a time limit (`timeout-minutes`) of two to several times its longest observed run: a job that hangs fails there instead of holding a runner for GitHub's default of six hours. GitHub's hosted macOS arm64 runners are sometimes all taken; GitHub then cancels a waiting job itself after about 15 minutes, with no step run ("The job was not acquired by Runner of type hosted even after multiple attempts"). When a push run on `main` fails, the `CI rerun` workflow (`.github/workflows/ci-rerun.yml`, `scripts/rerun-unacquired.py`) reruns its failed jobs, but only when every failure is such an unacquired job, or the `CI gate` and a platform's `rust` job that only report on it, at most three times per run, and only while no newer push to `main` has a CI run: a rerun goes back into the `main` concurrency group, where it would cancel that newer run's pending place. A job that ran a step and failed is never rerun. `cut` takes a run's latest attempt.

A push to `main` or a pull request that changed only `docs/releases/` (the release pull request `cut` opens, and the merge commit that brings it into `main`) does not repeat the Rust jobs or the Apple job: nothing they build or test reads that directory. `scripts/skip-rust-jobs.py` waits for this workflow's push run on the commit the change stands on (the commit before the push; the pull request's base, which it must not be behind) and skips them when that run passed, so a passed run always stands on Rust jobs that ran on the same code. They run when that run did not pass, when any other file changed, when the pull request is behind its base, or when GitHub could not say. The structure job still runs on every push; on a pull request its separate structure-input path check applies. The other jobs and the gate always run. The workflow also runs on `merge_group`, for GitHub's own merge queue, where the Rust jobs always run.

`cut` accepts only the **entire workflow's** completed successful run, never an individual successful job: the push run on the exact `main` commit it releases from, and the run of its release pull request (see "Only a tested commit is tagged" below).

Official GitHub cache actions restore Rust dependencies under a key made of the platform, the toolchain, the lockfile, every manifest and the workflow file: everything that decides how dependencies are built. Workspace packages are cleaned both after restoring and before saving a cache, so they are always rebuilt from the current checkout. Pull requests only read caches, and one whose key has no cache yet starts from `main`'s newest cache for its platform; only trusted main pushes write them. A push to `main` saves a cache only when its key has none, built from nothing, so there is one cache per dependency set rather than one per push. The release build uses no cache and always compiles from nothing: GitHub's cache scope does not let a tag read another tag's cache, so a cache saved there was never read. The release workflow builds the web assets once alongside native Linux/macOS builds, then packages and verifies each target on its native platform; publication still waits for both complete bundles.

- **No process documents.** Design notes, plans, proposals, specs, reviews, prototypes and runbooks are the maintainers' own thinking and are kept outside the repository. What a user or operator needs goes into the README, `docs/deployment.md` or the release notes; what a reader of the code needs goes into its comments. `python3 scripts/check-public-boundary.py --strict` (run by CI) rejects any other Markdown file, and anything under `docs/` other than `deployment.md`, `releases/` and `assets/`; test fixtures are exempt.

## Changes and releases

A version is chosen when it is released, never ahead on a branch:

- **What the three numbers mean.** Versions are `MAJOR.MINOR.PATCH`.
  - **PATCH** goes up with every ordinary release: features, fixes, interface changes, migrations that run by themselves. Clients and Nodes of the previous release keep working with the new Hub.
  - **MINOR** goes up (and PATCH starts again at 0) for a release that an operator must act on, or should know about before upgrading:
    - the protocol between Hub and Node or Hub and clients changes, so older Nodes or clients must be upgraded first;
    - a feature, setting, API or command-line form is removed or changes meaning;
    - configuration has to be changed by hand;
    - the upgrade cannot be undone by reinstalling the previous release (for example, a migration that older releases cannot read).

    Its release notes start with what to do.
  - **MAJOR** stays 0 until the interfaces and data formats are declared stable. It then becomes 1 once, by hand (`--version 1.0.0`).

  A change that needs a MINOR release says so in the first line of its fragment (`Needs a minor release: <why>`), and whoever cuts the release then passes `--minor`.
- **Release notes are fragments.** A change adds `docs/releases/unreleased/<item>.md` (its item, such as `ST-38.md`, or its branch name): what changes for the user, in a few sentences or bullets, with no version and no title. Do not write `docs/releases/X.Y.Z.md` on a branch; `python3 ops/cut-release.py lint` checks this.
- **Releasing:** after the change is on `main`, run `python3 ops/cut-release.py cut`. It selects a tested commit on `origin/main` as the release's base, gives it the next free version (one more than the highest `vX.Y.Z` tag), and commits the fragments joined into `docs/releases/X.Y.Z.md` on that base, removing them; that commit changes nothing else. Because `main` takes nothing but pull requests, the commit goes in as one: `cut` pushes it to `release/vX.Y.Z`, opens a pull request, waits for its CI run (release notes can skip Rust as above; a pull request behind main runs Rust again), merges it with a merge commit, and then pushes the annotated tag `vX.Y.Z` on the notes commit itself; the tag starts the Release workflow. Other pull requests keep landing on `main` meanwhile, and that does not matter: the merge commit joins the notes to whatever `main` has become, and fragments that arrived after the base stay on `main` for the next release. `cut` closes the release pull request and starts again, a few times at most, only when it does not merge cleanly (a fragment it removes was changed meanwhile), someone else released the version first, or the release branch was taken. The tag is pushed only after the merge, so a merge that fails never leaves a published release that `main` does not contain; a release whose pull request merged but whose tag did not land is finished by the next `cut`, which tags that notes commit as it is. `--dry-run` previews the current head's notes without selecting a tested base or releasing; `--minor` bumps the minor version. Releasing needs `gh` logged in with the right to open and merge pull requests and to push tags, and branch rules on `main` that allow merge commits and do not require pull requests to be up to date before merging.
- **Only a tested commit is tagged.** `cut` walks main's first-parent history since the last release and picks the newest commit whose own latest full push run completed successfully on both platforms. Newer running, cancelled or failed commits wait for the next release, with their fragments left on main. Cancelled runs never count as successful tests, and a pull request's run, with Linux Rust tests and conditional macOS checks, never stands for a push run. If no eligible commit passed, `cut` checks the current head, waits while it runs (`--ci-wait`, 45 minutes by default), and refuses when it failed or there is no push run. The notes commit then needs its release pull request's run to pass. The tagged commit is exactly that tested base plus the checked release notes, however far `main` has moved since. Investigate test failures before releasing; a rerun is appropriate for a resolved runner or service failure, not a substitute for fixing a flaky test. `--skip-ci` releases without the check, on purpose. If the Release build on the tag fails on a flake, rerun it the same way on the same tag; nothing is published until every target is built.
- **Database migrations** take their number when they are merged: the next free one in `hub-rs/crates/steve-store/migrations`, with a line appended to `LOCK`.
